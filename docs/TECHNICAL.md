# RealCamera — техническая документация

Версия мода: **0.8.4** (ветка `patch-0.8.5`). Платформа: **Minecraft 1.21.1, NeoForge 21.1.265**, Java 21,
ModDevGradle, маппинги Mojang + Parchment (2024.11.17). Пакет `dev.hackdanel.realcamera`, mod id `realcamera`.

Документ описывает, как устроен мод и почему он устроен именно так: каждую подсистему, её алгоритмы, числа,
принятые решения и известные ограничения. Пользовательское управление описано в `README.md`, исходный план — в
`~/.claude/plans/mellow-munching-sonnet.md`, отчёты по этапам — в `docs/stage*.md`, исправления после внешнего ревью —
в `docs/review-fixes.md`. Если документ расходится с кодом, прав код.

## 1. Цели и принципы

**Цель.** Фотосъёмка в Minecraft, которая ведёт себя как настоящая: реальные камеры, объективы и плёнки с их
характеристиками, ручная экспозиция, физически осмысленная оптика (ГРИП, боке, смаз, шум, дисторсия), снимок как
предмет (печать, рамка, альбом), редактор с RAW, плёнка с проявкой, серверная оценка кадров.

**Ключевые принципы, которые прошли через весь проект:**

- **Физика, а не «эффекты».** Каждый эффект считается из реальных величин: формула тонкой линзы для круга рассеяния,
  APEX для экспозиции, диск Эйри для дифракции, модель переноса фотонов для шума, Рэлеевская поляризация неба,
  закон Шварцшильда для плёнки. После этапа 8 конвейер сверили с опубликованной физикой (раздел E в
  `docs/review-fixes.md`).
- **Поведение задаётся спецификацией, а не кодом.** Что умеет камера (режимы, типы затвора, экспонометр, вспышка с
  электронным затвором, встроенный объектив/накопитель) — поля JSON. Добавить камеру = добавить запись в каталог.
- **Снимок — настоящий рендер мира.** Кадр рендерится игрой в разрешении матрицы и только потом обрабатывается
  на CPU. Никаких «нарисованных» фото.
- **Сервер — источник правды.** Что попало в кадр, сервер определяет сам по своему состоянию мира; параметры с
  клиента ограничиваются возможностями камеры. Содержимое карт памяти живёт на сервере.
- **Чистая математика отделена от игры.** Пакеты `optics/` и `processing/` не используют классы Minecraft и покрыты
  юнит-тестами.
- **Все ассеты генерируются скриптами** (`tools/`). Никаких изображений и логотипов производителей. Бренды и модели
  используются только как названия (номинативное использование, дисклеймер в README). Проект некоммерческий, без
  публикации на CurseForge/Modrinth без решения владельца.

## 2. Сборка, запуск, зависимости

| Что | Версия / где |
|---|---|
| NeoForge | 21.1.265 (`gradle.properties`) |
| Parchment | 2024.11.17 для 1.21.1 |
| Sodium | `mc1.21.1-0.8.13-neoforge` (только dev, конфигурация `devMods`) |
| Iris | `1.8.14-beta.1+1.21.1-neoforge` (только dev, `devMods`) |
| JEI / EMI / REI | 19.70.0.469 / 1.1.24+1.21.1 / 16.0.799 (`compileOnly`, рантайм по `-Pviewer=`) |

Системная Java может быть новее 21: Gradle сам скачивает JDK 21 (foojay toolchain).

Основные задачи: `./gradlew build`, `./gradlew test`, `runClient`, `runClient2` (второй клиент, ник Player2),
`runServer` (EULA владелец принимает сам), `runClientAutotest -Pautotest=<сценарий>`.

**Решение по Sodium/Iris в dev.** Sodium 0.8 упакован как jar-in-jar и ломается, если грузить его с dev-classpath.
Поэтому релизные jar-ы Sodium и Iris из конфигурации `devMods` копируются в `mods/` каждой папки запуска.
`-PnoShaders` отключает копирование.

**Автотесты в игре.** `runClientAutotest` запускает клиент в `run-autotest/`, сам создаёт мир, строит сцену, снимает,
печатает и т. д. Результат — строки `[autotest] PASS/FAIL` в логе, скриншоты в
`run-autotest/screenshots/autotest/`, снимки в `run-autotest/screenshots/realcamera/<дата>/`. Сценарии:
`stage1`…`stage8`, `dof`, `pose`. Флаги: `-PcaptureWarmup=N` (кадры прогрева), `-Pviewer=jei|emi|rei`,
системные свойства `realcamera.fastLab` (лаборатория ×10 быстрее), `realcamera.debugDumps` (сырой кадр и карта
глубины рядом с каждым снимком). Шейдерпаки, требующие `#version … compatibility` (IterationT), на Mesa
запускаются только с `allow_glsl_compat_shaders=true`.

**Разделение клиента и сервера.** Один source set. Клиентский код подключается через `@Mod(dist = Dist.CLIENT)` и
`@EventBusSubscriber(value = Dist.CLIENT)`. Общий код обращается к клиенту только через интерфейс `ClientBridge`
(реализация `client/ClientBridgeImpl`): так выделенный сервер никогда не загружает клиентские классы. Пакеты
сервер→клиент регистрируются в общем коде и передаются через `ClientBridge.handlePayload`.

**Миксины только там, где нет событий NeoForge**: проверка заказов газеты в торговле (3 миксина) и фокус ГРИП
шейдерпака (`@Pseudo`, Iris необязателен). Всё остальное — события (`ViewportEvent.ComputeFov`,
`RenderLevelStageEvent`, `RenderGuiEvent`, `RenderFrameEvent`, `InputEvent`, …) и расширение enum
(`META-INF/enumextensions.json` для позы рук).

## 4. Каталог оборудования (data-driven)

### 4.1 Решение

Камеры, объективы и прочее **не отдельные классы предметов**. Есть несколько общих предметов (`camera_body`,
`lens`, `mount_adapter`, `teleconverter`, `flash`, `filter`, `battery_grip`, `battery`, `memory_card`,
`film_roll`), а конкретная модель — data-компонент с `ResourceKey` на запись в **синхронизируемом datapack-реестре**
(`registry/RCRegistries`, регистрируется через `DataPackRegistryEvent.NewRegistry` с сетевым кодеком). Клиент
получает каталог с сервера. Новую камеру можно добавить JSON-файлом без кода.

Реестры (`data/realcamera/realcamera/<реестр>/*.json`) и текущий объём:

| Реестр | Записей | Record |
|---|---|---|
| `camera_body` | 39 | `CameraBodySpec` |
| `lens` | 63 | `LensSpec` |
| `mount` | 17 | `MountSpec` (рабочий отрезок, диаметр горла) |
| `mount_adapter` | 25 | `AdapterSpec` |
| `teleconverter` | 10 | `TeleconverterSpec` |
| `battery_type` | 24 | `BatteryTypeSpec` (ёмкость в кадрах) |
| `memory_card_type` | 9 | `MemoryCardTypeSpec` (форма, ГБ, МБ/с) |
| `color_profile` | 32 | `ColorProfileSpec` |
| `flash_type` | 5 | `FlashSpec` |
| `filter_type` | 52 | `FilterSpec` |
| `grip_type` | 2 | `GripSpec` |
| `step_up_ring` | 15 | `StepUpRingSpec` (входная и выходная резьба) |
| `film_stock` | 9 | `FilmStockSpec` |

Названия: ключи `realcamera.<реестр>.<namespace>.<path>` в `en_us.json` / `ru_ru.json` (`item/SpecNames`).

**Генератор каталога.** Начиная с этапа 6 каталог описан в `tools/catalog.py` (тушки, объективы, байонеты,
адаптеры, ТК, батареи, карты, фильтры). `gen_catalog.py` пишет JSON реестров и en/ru названия; `gen_assets.py`
читает тот же файл для моделей (`style` тушки, `look` объектива); `gen_recipes.py` — для рецептов (tier/kind).
Порядок после правки: gen_catalog → gen_assets → gen_recipes. Записи ранних этапов — рукописный JSON.
`CatalogTest` проверяет ссылки, правило рабочего отрезка для адаптеров, наличие моделей, названий и рецептов.

**Ограничение кодеков.** `RecordCodecBuilder` принимает не больше 16 полей в группе. Поэтому `CameraBodySpec`
разбит на вложенные record-ы (`Info`, `Shutter`, `Af`, `Flash`, `Film`), а `CameraSettings` генерируется скриптом
`tools/gen_settings.py` двумя группами кодеков.

### 4.2 Тушка (`CameraBodySpec`)

- `info`: бренд, EXIF Make/Model (`SONY` / `ILCE-7M4`), tier, тип (`mirrorless`, `dslr`, `rangefinder`, …).
- `mount`, `sensor` (ширина/высота мм, МП, base ISO, диапазон ISO, ДД в EV, коэффициенты шума яркости/цвета).
  Из сенсора выводятся кроп-фактор (диагональ 43.27 мм / диагональ), аспект и **сторона выходного файла** по классу
  разрешения: ≤16 МП → 1280 px, ≤26 → 1920, ≤45 → 2560, ≤61 → 3200, больше → 3840.
- `viewfinder`: `evf`, `ovf`, `rangefinder`, экран.
- `shutter`: `mech_min`/`elec_min` (самые короткие выдержки; `mech_min = 0` — механического затвора нет, Z8/Z9),
  `max` (самая длинная, по умолчанию 30 с), `rated_life`, `sound`, `readout_ms` (считывание матрицы для rolling
  shutter), `burst_mech`/`burst_elec`, `buffer_shots`, флаги `efcs`, `leaf` (центральный затвор), `full_mech`.
- `af`: множитель скорости, `low_light_ev` (порог AF, измеренный с f/1.2), `subject_detect`
  (`none`/`face`/`eye`/`animal`/`bird`/`vehicle`, каждый уровень включает предыдущие).
- `ibis_stops`, `battery_type`, `battery_drain` (= ёмкость батареи / CIPA кадров; дробное), `card_forms`,
  `weather_sealing` (0/1/2), `color_profiles`, `flash` (`built_in_gn`, `sync`), `model`.
- `film` (только плёночные): `format` (135/120), `mechanical`, разрешённые `modes`, `meter`
  (`battery`/`selenium`/`none`), `iso_dial` (`manual` по умолчанию / `dx_override` / `dx` / `none`).
- `fixed_lens`: встроенный объектив компакта на псевдо-байонете `realcamera:fixed`. Слот объектива заполняется
  тушкой на тике инвентаря и блокируется; подсказка называет встроенный объектив и до этого (JEI/EMI, `/give`).
  Во вкладке креатива у таких камер только готовый комплект, без варианта «только тушка».

Производные правила (в коде спеки, не в логике камеры):

- **Типы затвора** (`shutterTypes`): механический — если есть и `full_mech`; EFCS — если есть механический, `efcs`
  и не `leaf`; электронный — у беззеркалок с `elec_min > 0`, но **не** у зеркалок и плёнки. У R8/R50 нет полностью
  механического режима.
- **Вспышка с электронным затвором** только при считывании ≤ 8 мс (стековые матрицы); синхронизация тогда
  `max(readout·1.2, 1/250)`.
- **Встроенный накопитель** (Hasselblad X2D): все `card_forms` начинаются с `internal` — слот карты заполняется
  тушкой и блокируется.
- **Режимы экспозиции** плёночных тушек ограничены `film.modes`; недоступный режим заменяется следующим
  доступным (`coerceMode`).

### 4.3 Объектив (`LensSpec`)

Бренд, EXIF-имя, байонет, `image_circle` (ff/apsc/mft/mf), фокусные, диафрагма на широком и длинном конце,
минимальная диафрагма, МДФ, AF (`motor`, `speed`), `ois_stops`, `filter_mm` (0 = фильтр не ставится),
`tc_compatible`, модель. Блок `optics`: число и скруглённость лепестков, виньетирование (EV), резкость, дисторсия
на концах зума (k1), латеральная ХА (px на 4K), сила бликов, характер боке (`smooth`/`busy`/`swirl`/`bubble`),
проекция (`rectilinear` или фишай `equisolid`/`stereographic`/`equidistant`), `tilt_shift` (градусы/мм),
`max_magnification`, `loca` (продольная ХА относительно типичной; APO = 0.2×), `transmission_loss_ev`,
`character` (`spherical` −1..1, `field_curvature` мм, `apodization` 0..1, `obstruction` 0..0.6, всё по умолчанию 0;
вложенный record, потому что в `Optics` уже 15 полей из 16 возможных).

Решения:

- **Переменная диафрагма зумов** растёт логарифмически по фокусному и округляется **до 1/3 ступени** (f/3.5, 4,
  4.5, 5, 5.6), как на реальных камерах.
- **Максимальное увеличение** берётся из каталога; без значения — оценка тонкой линзы, ограниченная 0.25 (обычные
  объективы фокусируются ближе за счёт внутренней фокусировки, а не макро).
- **Фокусная «дыхательность»** (`framingAt`): на бесконечности — номинальное фокусное, на МДФ — увеличение из
  паспорта; между ними геометрическая интерполяция по диоптриям. Зум заявляет увеличение для длинного конца и
  масштабирует его с фокусным. «Дыхание» ограничено 0.75× (иначе единственная МДФ каталога, взятая для короткого
  конца, давала до 2× слишком широкий кадр).
- **T-stop**: по умолчанию 0.15 EV у фиксов, 0.3 EV у зумов; ТК добавляет 0.1 EV. TTL-замер это компенсирует,
  камера без экспонометра — нет.
- **LoCA**: сдвиг фокуса красного/синего относительно зелёного ∝ светосиле и √фокусного; ТК увеличивает его в k².

### 4.4 Байонеты и адаптеры

**Физическое правило:** адаптер возможен, только если рабочий отрезок байонета объектива **больше**, чем у тушки
(зеркальные и плёночные стёкла на беззеркалки, наоборот нельзя). У адаптера: `af` (`full`/`slow`/`none`),
множитель скорости AF, `electronic` (передаются ли диафрагма и данные; «глупый» адаптер даёт в EXIF объектив `----`),
длина (для модели). Все 25 адаптеров проверяются `CatalogTest`.

EF-S и RF-S — не отдельные байонеты, а `canon_ef`/`canon_rf` с кругом изображения `apsc`. В подсказке кроп-тушка
(кроп > 1.4) и APS-C-объектив показывают APS-C-имя байонета, если оно есть (`APSC_MOUNT_NAMES` в `tools/catalog.py`
→ ключ `realcamera.mount.realcamera.<key>.apsc`, `SpecNames.mount`): Canon EF-S, Canon RF-S. У Nikon DX, Sony E
APS-C и Fujifilm X байонет называется так же, как у полного кадра.

### 4.5 Прочие записи

- **Телеконвертеры**: множитель фокусного и диафрагмы, AF-множитель, резкость, байонет; ставятся только на
  `tc_compatible` объективы своего байонета.
- **Батареи**: ёмкость в «кадрах» — единица, в которой расходуется всё.
- **Карты**: SD UHS-I/II, CFexpress A/B, разные объёмы и скорости записи; встроенный SSD X2D (`internal_*`).
- **Цветовые профили**: контраст, насыщенность, монохром, тинт по каналам, подъём теней (Sony Creative Look,
  Canon Picture Style, Nikon Picture Control, симуляции Fujifilm, Leica, Hasselblad, Panasonic, OM).
- **Вспышки**: ведущее число (ISO 100, м), перезарядка, HSS, ёмкость (полных импульсов).
- **Ручки**: список тушек и тип батареи.
- **Фильтры**: генерируются из `FILTER_KINDS` в `tools/catalog.py` (вид × диаметр 67/77/82/95/112, ключ
  `<base>_<size>`); виды в разделе 14.2. Повышающие кольца — из `STEP_UP_RINGS` там же (по одному на резьбу
  объективов, до следующего выпускаемого размера фильтра, ключ `step_up_<in>_<out>`).
- **Плёнки**: раздел 21.1.

### 5.3 Настройки камеры (`CameraSettings`)

Хранятся **на самом предмете** (камера «помнит диски», если её передать или выбросить). Генерируются
`tools/gen_settings.py` (record, кодеки в двух группах, `withX`-методы). Поля: режим (Auto/P/A/S/M), индексы
выдержки/диафрагмы/ISO (−1 = Auto ISO), экспокоррекция в 1/3 EV, баланс белого (Auto, Дневной, Облачно, Тень, Лампы,
Флуоресцент, Вспышка, Кельвин) и кельвины, замер (матричный, центровзвешенный, точечный), режим фокуса
(AF-S/AF-C/MF), дистанция фокуса, фокусное, качество (Fine/Normal), профиль, DISP, выбранный параметр, тип затвора,
режим съёмки (покадровый, серия Lo/Hi/Hi+, таймер 2/10 с), формат (JPEG/RAW/RAW+JPEG), зона AF (широкая, зона,
точка, трекинг) и координаты точки, распознавание объектов, пикинг, стабилизация, кроп-режим APS-C, коррекция
объектива, режим вспышки (выкл, заполняющая, по второй шторке, авто) и её компенсация, tilt, shift, шумоподавление
длинных выдержек.

**Шкалы** (`optics/ExposureScales`): выдержки 1/32000…30 с с шагом 1/3 + Bulb (индекс 61, только M), диафрагмы
f/1.0…f/32, ISO 50…204800, экспокоррекция ±5 EV. Для физики берутся точные значения (ISO = 100·2^((i−3)/3)), в EXIF
пишутся номинальные (1/8000, 0.3", 30"), как делают камеры.

**Синхронизация.** `Viewfinder.sendSettings` меняет настройки локально сразу и отправляет `UpdateSettings` на
сервер. Он же ставит их на клиентский стек: иначе при повторном поднятии камеры до прихода обновления слота
читались старые фокус и точка AF.

### 5.4 Как сеть адресует камеру

`camera/CameraRef` — рука (main/off) или id сущности штатива. Сервер разрешает её через
`ServerPhotoService.resolve`, меняет стек и обязан вызвать `commit()` у полученного `Handle` (камера на штативе —
копия, хранимая в данных сущности).

## 6. Оптическая цепочка

`camera/OpticalChain` — **единственный** путь расчёта оптики: тушка → адаптер → телеконвертер → объектив.
Результат вычисляется один раз и содержит:

- **Проверку совместимости** (`problem()`): байонеты, правило адаптера, ТК только на совместимый объектив. Причина
  отказа идёт в сообщения и проверку слотов.
- **Эффективную матрицу.** Объектив APS-C на полном кадре: в режиме `CROP_AUTO` — кроп (меньше файл), в `CROP_OFF`
  — полная матрица с тёмными углами малого круга изображения. Canon EF-S/RF-S рассчитаны на кроп 1.6, остальные на
  1.5. Любой объектив с кругом меньше матрицы виньетирует (полнокадровое стекло на среднем формате; Planar 6×6 на
  GFX — нормально).
- **Эффективное фокусное и диафрагму** (ТК умножает обе), фокусное с учётом дыхания на дистанции фокуса.
- **Скорость AF** = тушка × мотор объектива × адаптер × ТК; адаптер `none` — только ручной фокус.
- **Порог AF в темноте**: паспорт тушки дан для f/1.2; более тёмный объектив теряет 2·log2(N/1.2) EV.
- **Предел фазового AF зеркалок**: f/5.6 у начальных, f/8 у остальных (тёмный зум с ТК 2× становится ручным).
  Беззеркалки фокусируются по матрице при любой диафрагме.
- **Потери света**: T-stop, ТК, растяжение на макро (bellows factor, 2 EV на 1:1).
- **Увеличение**, **LoCA**, **EXIF-имя объектива**, сдвиг и наклон тилт-шифта, угол рендера.

## 7. Видоискатель и управление

### 7.1 Клавиши

Регистрируются через `RegisterKeyMappingsEvent` с собственным контекстом конфликтов `CAMERA_IN_HAND`: активны
только с камерой в руке (или при взгляде через штатив) и не мешают ванильным.

| Клавиша | Действие |
|---|---|
| ПКМ (удерж.) | поднять камеру к глазу |
| ЛКМ | спуск (сначала AF) |
| колесо | зум / параметр у фикса |
| Z / X | выбрать параметр (выдержка, диафрагма, ISO, EV, ББ; TILT/SHIFT у тилт-шифта) |
| Ctrl + колесо | изменить параметр |
| Alt + колесо | ручной фокус |
| M / F | режим экспозиции / режим фокуса |
| Tab | DISP (полный, гистограмма, базовый, чистый) |
| P / G | просмотр / меню камеры |
| H | лупа ×5 |
| B | режим съёмки |
| V | режим вспышки |
| N, стрелки | зона AF, сдвиг точки |
| R | AF-ON |
| J | энциклопедия (вне камеры) |
| Shift + ПКМ | открыть камеру (слоты) |

С камерой у глаза атака ЛКМ отменяется (`InputEvent.InteractionKeyMappingTriggered`), колесо не листает хотбар.

### 7.2 Поднятие камеры

У `CameraBodyItem` **нет ванильной анимации использования**: рендерер выбрал бы позу подзорной трубы раньше, чем
спросил предмет. Поднятие к глазу занимает `Viewfinder.RAISE_TICKS` (≈ четверть секунды), анимация от бедра к глазу
в первом лице идёт через `CameraItemExtensions`; видоискатель включается только когда камера у глаза. Рука
отменяется всё время, пока камера используется (не только при активном видоискателе): у позы подзорной трубы нет
трансформации первого лица, и модель на один кадр оказывалась у глаза.

### 7.3 Поле зрения

Вертикальный FOV из высоты эффективной матрицы и эффективного фокусного (`Optics.verticalFovDeg`) через
`ViewportEvent.ComputeFov` (без миксина). Кадр матрицы вписывается в окно: шире — боковые поля, уже — сверху и снизу.
У дальномеров вид шире кадра, рамки отмечают снимок. У фишаев рендерится ограниченный прямолинейный кадр (раздел
13.1). При сдвиге тилт-шифта вид наклоняется вверх на atan(shift/f) (в видоискателе вертикали ещё сходятся,
исправляет только снимок).

### 7.4 Типы видоискателя (`ViewfinderHud`)

- **EVF (беззеркалки):** живое превью снимка (7.6), гистограмма того, что получится (`FrameSampler`, асинхронное
  чтение через два PBO), шкала экспонометра, рамки AF и боксы объектов, заряд, оставшиеся кадры, сетка, пикинг,
  лупа. Bulb в превью — как 1 с.
- **OVF (зеркалки, плёночные SLR):** без симуляции экспозиции, затемнённые края пентапризмы, зелёная строка данных,
  узор точек AF. Оптический видоискатель не тратит батарею во время смотрения.
- **Дальномер (Leica M):** вид шире, светлые рамки под фокусное, **дальномерное пятно**: «призрак» смещён вбок на
  ошибку фокуса (1/фокус − 1/дистанция объекта) и сливается, когда фокус наведён. Живой ГРИП там выключен (окно
  дальномера показывает всё резким).
- Затемнение видоискателя, пока затвор открыт на длинной выдержке.
- Выделение блока (контур) отменено в видоискателе и во время захвата (толщина линии ещё и ломается при ресайзе).
- **Мод-слои GUI рисуются даже при `hideGui`**: HUD видоискателя пропускает себя при `PhotoCapture.capturing()`,
  иначе маска и превью попадали в снимок.

### 7.5 Живая глубина резкости (`client/render/DofPreview`)

Видоискатель размывается так же, как будет размыт снимок: выставленная диафрагма, фокус, который двигается вместе
с мотором AF и кольцом, наклон тилт-шифта.

- В `RenderLevelStageEvent` AFTER_LEVEL буфер глубины ещё содержит мир (до руки и GUI его очищают): проход 1
  превращает глубину в знаковый радиус размытия в полном разрешении.
- Проходы 2–4: уменьшенный цвет + радиус, дисковое размытие, смешивание резкой и размытой картинки в полном
  разрешении. Разрешение прохода 1/2…1/8, чтобы предел радиуса (15 % высоты экрана) совпадал со снимком, а цена на
  пиксель оставалась ограниченной. Спираль выборок доходит только до реального наибольшего размытия кадра (не до
  предела 15 %), поэтому малое размытие тоже получает выборки у центра.
- Диск выборки — той же формы, что на снимке (`include/dof_bokeh.glsl` = `BokehKernel`): многоугольник по числу
  лепестков (перевёрнутый перед плоскостью фокуса), профиль стиля боке.
- Малое размытие (до ~2 пикселей уменьшенного прохода) собирается в композите в полном разрешении: иначе проход в
  1/8 добавлял свою «кашу» и превью было заметно размытее снимка.
- Без шейдерпака размытие идёт сразу после уровня; с Iris — на `RenderGuiEvent.Pre` (Iris дорисовывает картинку
  после AFTER_LEVEL); при скрытом GUI (F1) — в конце кадра.
- Выключено во время захвата (у снимка свой точный ГРИП), на дальномерах, в конфиге (`liveDepthOfField`) и с
  шейдерпаком, которому нельзя доверять глубину (раздел 26.1).
- Контраст для AF меряется в той же точке, **до** размытия.
- **Зеркалки (`ovf`)**: видоискатель показывает объектив открытым (`Viewfinder.viewAperture`), клавиша репетира `Y`
  (`RCKeys.DOF_PREVIEW`, удержание) прикрывает до рабочей; видоискатель темнеет на величину прикрытия, метка «DOF».
- **Шкала ГРИП** (`ViewfinderHud.dofScale`): 1.5 с после поворота кольца фокуса — шкала в диоптриях (∞ справа),
  полоса резкости, фокус, H (гиперфокальное); в верхней строке EVF — границы резкости. CoC = 0.03 мм / кроп;
  с тилтом не показывается.

### 7.6 Живое превью снимка в электронном видоискателе (`client/render/EvfPreview`)

> Новая работа: на момент написания документа в рабочей копии, ещё не в коммите.

Электронные видоискатели (`evf`, гибридный, только экран; цифровые тушки) показывают **как будет выглядеть
снимок**, попиксельно. Шейдер `realcamera_evf` работает на готовой картинке после живого ГРИП и до GUI и выполняет
попиксельную часть проявки в порядке снимка: цветной фильтр, осветление тёмной сцены (по кривой света игры, с
шейдерпаком — `FrameSampler.meteredLuminance` + `ShaderCompat.packRelight`, сглажено), ошибка экспозиции, GND,
виньетирование и его внутрикамерная коррекция, шум матрицы на текущем ISO, отсечка, ББ (выгоревшее нейтрально),
плечо светов, цветовой профиль.

- Параметры строятся тем же `PhotoCapture.digitalParams`, что и для снимка.
- `processing/LiveView` — Java-эталон шейдера: проверяется против `ImagePipeline` в `LiveViewTest` и даёт гистограмму.
  **Шейдер и `LiveView` меняются только вместе.**
- В превью нет того, что разносит свет по кадру (ГРИП рисует свой проход; смаз, блики, mist, star, дисторсия,
  поляризатор, вспышка) и износа.
- Выключено на оптических и дальномерных видоискателях, на плёнке и во время захвата. Если кадр уже показывает вид
  снимка, HUD не затемняет и не осветляет его повторно.

## 8. Экспозиция и замер

### 8.1 Яркость сцены (`client/camera/SceneMeter`)

Игровой свет переводится в **физический EV (ISO 100)**. Калибровка против реального света:

| Условие | EV |
|---|---|
| ясный полдень | 15 |
| пасмурно | 13 |
| дождь | 11–12 |
| гроза | ≈ 10 |
| закат | ≈ 11 |
| конец гражданских сумерек | ≈ 0.5 |
| полная луна | −2.5 |
| новолуние (звёзды) | −9 |
| открытая тень (1 блок под навесом) | −2.6 от солнца |
| 3 блока внутрь | −6.6 |
| глубина комнаты | ≈ −10 |
| комната с факелами | ≈ 6 |

Небесный свет зависит от высоты солнца, погоды и фазы луны; блочный — от уровня. Небесный свет в игре спадает
куда медленнее реального: один блок под навесом — уже настоящая тень. Измерения без неба (Незер, Энд) имеют
фиксированную яркость.

**Цветовая температура сцены**: тёплое низкое солнце, нейтральный полдень, холодная облачность; луна ≈ 4100 K;
тень (небесный свет < 15) освещена только синим небом; огонь (факел, фонарь, лава) ≈ 1900 K. Auto WB исправляет её
частично, как реальные камеры.

### 8.2 Замер

Сетка 9 × 6 весов (матричный, центровзвешенный, точечный по зоне AF). Лучи из камеры попадают в блоки и сущности;
EV точки — EV освещённого воздушного блока перед гранью, или неба.

**Отражённый свет обманывает экспонометр** (как настоящий): альбедо поверхности берётся из яркости её map-colour
относительно 0.3 (среднее типичной сцены). Снег и белое недоэкспонируются, уголь и тёмное — переэкспонируются.

Экспонометр видит через объектив: потери фильтра, T-stop, растяжение на макро уже в показаниях. Плёночные камеры:
батарейный экспонометр без заряда не работает, у Зенита селеновый (без батареи), у Hasselblad 500C/M экспонометра
нет.

### 8.3 Программа (`optics/Exposure`)

APEX: Av = log2(N²), Tv = −log2(t), EV100 = Av + Tv − log2(ISO/100). `Exposure.solve` выбирает
диафрагму/выдержку/ISO по режиму, возвращает индексы и остаточную ошибку (Δ > 0 — переэкспозиция).

- **Программная линия**: f/4 на EV 10, закрывается на полступени за каждый EV, в пределах объектива и не дальше f/11;
  зависит от ISO.
- **Auto ISO** начинается с base ISO (не с расширенного низкого) и не опускается ниже чувствительности плёнки; верх
  по умолчанию 12800. ISO ниже базового теряет запас по светам.
- **Вспышка в Auto/P/A** ограничивает выдержку синхронизацией (без полосы); полоса шторки — только если выдержку
  короче синхронизации выставили вручную в S/M.
- **Auto** — всё автоматически, вспышка в режиме «авто» срабатывает в темноте.

### 8.4 Правильная экспозиция = средне-серый

Игра рисует ночь и пещеры тёмными. Камера, правильно экспонированная по замеру, должна дать снимок, где замеренная
область — средне-серая, как бы темно ни нарисовала игра. `PhotoCapture.relight` вычисляет **глобальный** множитель из
кривой освещения игры в замеренных точках (до 16× ночью или в тёмной пещере). Попиксельного пересвета нет: сетка
света слишком грубая и давала бы ореолы (известное ограничение: при замере по тени освещённый солнцем фон не
пересвечивается сильнее, чем в игре).

Следствие (после ревью, B7): реальный ночной EV без «ползунка яркости». Ночью нужен штатив или высокий ISO — как в
жизни.

## 9. Автофокус и ручной фокус

### 9.1 Что видит AF

- Лучи AF, пикинга и дальномера попадают в **контур блока** (selection box), а не в форму коллизии: трава, цветы,
  саженцы, посевы и факелы видны.
- **AF нужна деталь.** `FrameSampler.contrastAt` меряет локальный контраст готового кадра вокруг точки AF: средняя
  разница яркости соседних блоков 3 × 3 пикселя относительно средней яркости (не зависит от яркости, не реагирует на
  дизеринг шейдерпаков). Измерено (ваниль / Complementary): чистое небо 0.0001 / 0.0024, белый бетон 0.0022 / 0.0042,
  луг 0.018 / 0.03, булыжник 0.16 / 0.13. Ниже порога объектив «рыщет» через весь диапазон (до ближнего конца, на
  бесконечность и обратно) и сдаётся — снимок не делается; на слабой детали фокус медленнее и менее точный. AF-C на
  бесструктурной области удерживает фокус.
- **Точность**: фазовый AF промахивается на долю глубины резкости при открытой диафрагме (считается в диоптриях, где
  ГРИП симметрична: 1/ближн. − 1/дальн. = 2/H). Ошибка больше у порога освещённости, с подсветкой и на слабой детали;
  заметна почти только на открытой диафрагме.
- **Темнота**: ниже `low_light_ev` (с поправкой на светосилу) AF не наводится. У цифровых тушек есть
  **подсветка AF** (объекты до 5 м, медленнее) — добавлена после того, как реальный ночной EV «убил» AF.
- **Скорость**: мотор AF (тушка × объектив × адаптер × ТК) ограничивает и слежение AF-C.

### 9.2 Зоны и распознавание

Зоны: широкая, зона, точка (стрелки двигают), трекинг. `SubjectDetector` ищет людей (игроки, жители, гуманоиды),
животных, птиц и транспорт по классу тушки, проецирует боксы сущностей в кадр, проверяет видимость лучом, выбирает
самого заметного, отдаёт глаз/центр; AF-C перенаходит отслеживаемую сущность. Широкая/зона раньше возвращали
центровзвешенную оценку вместо дистанции — исправлено.

### 9.3 AF-ON и ручной фокус

- **AF-ON (R)**: фокусировка «задней кнопкой». После неё ЛКМ снимает без перефокусировки, в AF-C слежение идёт, пока
  кнопка нажата; в видоискателе «AF-L».
- **MF**: Alt + колесо, шкала в метрах; **пикинг** — ячейки сетки глубины лучей внутри ГРИП подсвечиваются; лупа ×5.
- AF-S эмулирует полунажатие: ЛКМ сначала фокусирует, затем спуск (задержка = время AF).

## 10. Затвор, серия, буфер, питание

- **Типы**: механический, EFCS (тише, тот же диапазон), электронный (бесшумный, без износа, rolling shutter,
  вспышка только на быстрых матрицах). Набор звуков по тушке: беззеркалка, удар зеркала зеркалки, тихий
  центральный/дальномерный. Звук слышат окружающие (кроме электронного затвора).
- **Режимы**: покадровый, серия Lo/Hi/Hi+, таймер 2/10 с. Таймер продолжает идти, если фотограф отошёл от штатива
  (селфи).
- **Буфер**: кадры ждут проявки и загрузки; глубина `buffer_shots`, опустошение — со скоростью записи карты
  (размер файла / МБ/с). У плёнки буфера нет. Фактическая скорость серии ограничена рендером в разрешении матрицы
  (≈ 3 кадр/с на тестовом iGPU с шейдерами).
- **Проявка** идёт в собственном пуле на половине ядер, чтобы игра продолжала рендерить во время серии.
- **Bulb**: затвор открыт, пока держишь ЛКМ (только M).
- **Шумоподавление длинных выдержек** (по умолчанию вкл): тёмный кадр той же длительности, камера занята столько же.
- **Заклинивший затвор** блокирует все типы спуска; камеру всё ещё можно поднять (она показывает ошибку).
- **Питание**: кадр снимает `battery_drain` единиц (дробное, округляется случайно, так что в среднем точно); EVF и
  экран тратят понемногу во время работы; сначала расходуется ручка, потом батарея тушки; в холодных биомах ×1.5.
  Без заряда камера не включается, кроме механических плёночных (FM2, K1000, OM-1, M6, Зенит, Hasselblad) — у них
  отключается только экспонометр.

## 11. Захват кадра

`client/capture/PhotoCapture`. Решения этапа 0 (`docs/stage0-capture.md`) и последующих:

1. **Точка захвата** — `RenderFrameEvent.Pre/Post`. В Pre ставится `options.hideGui = true` (прячет HUD и руку,
   Iris это уважает), в Post читается основной render target (Post срабатывает до блита на экран, восстановление
   состояния не мелькает). Без миксина.
2. **Высокое разрешение без шейдерпака**: временно меняется размер `Window` и основного render target,
   вызывается `GameRenderer#resize`, рендерится **один прогревочный кадр** (без него полоса неба/тумана у горизонта
   чёрная), снимается следующий, всё восстанавливается. Прогревочные кадры очищаются в чёрный: изменённый target
   блитуется в окно в своём размере и выглядел как увеличенный угол («прыжок» вида).
3. **С шейдерпаком окно НЕ меняет размер** (`Active.noResize`): ресайз пересоздаёт буферы пака и сбрасывает его
   автоэкспозицию, временное накопление и таймер заставки (IterationT выдавал серый кадр с надписью
   «Iteration 3.2.0»). Кадр рендерится в размере окна (с более высоким FOV, если окно уже матрицы), снимок —
   центральная вырезка с аспектом матрицы (`fw/fh/cx/cy`). Для большего разрешения — развернуть окно.
4. **Глубина**: буфер глубины того же кадра читается в AFTER_LEVEL и линеаризуется проекцией этого кадра. Параллельно
   `CameraRays` пускает сетку лучей (глубина, освещённость поверхности, попадания в сущности, поле движения).
   Глубина GPU используется, если согласуется с сеткой (`DepthUpsampler.agrees`): GPU может видеть ближе (трава без
   коллизии) или дальше (бокс сущности толще модели), но никогда заметно дальше блока, в который попал луч. Иначе
   сетка апскейлится joint-bilateral (каждый пиксель берёт глубину из ближайшего по цвету из 4 узлов). Слой одной
   фиксированной глубины, противоречащий лучам (некоторые паки пишут ночное небо на 0.6 м), помечается неизвестным и
   заполняется из сетки. Глубина измеряется вдоль оптической оси; у сдвинутого объектива — вдоль горизонтальной оси
   (плоскость фокуса остаётся параллельной матрице).
5. **Длинные выдержки (≥ 1/4 с) и Bulb** длятся реальное время: каждый кадр рендера суммируется в линейном свете
   на CPU через двойные PBO (`glGetTexImage` в PBO, маппинг предыдущего). Движение оставляет шлейфы, огни — линии,
   звёзды — треки. Накопление в разрешении окна (4K-кадр с шейдерами стоит ≈ 0.5 с).
6. **Чужие вспышки** во время открытого затвора добавляются как сетка света с тенями (раздел 25.1).
7. Всё, что известно в момент спуска, замораживается в `PhotoCapture.Shot` (параметры, движение, солнце, тепло
   матрицы, замер); проявка, экспорт и загрузка идут в рабочем потоке, кадры ждут в буфере.

Дальность прорисовки сущностей на время захвата поднимается, чтобы телевик видел далёкие объекты (и анализ кадра
засчитывал только то, что клиент реально видит).

## 12. Конвейер проявки (ImagePipeline)

`processing/ImagePipeline` + `ImageParams`, чистая Java. Работает в линейном float RGB. Разделён на две части, как
настоящая камера:

**`developSensor`** — всё до процессора камеры (то, что содержит RAW), по ходу света:

1. Пропускание фильтра (цветные нормированы по яркости: камера мерит через фильтр, поэтому красный фильтр делает
   синее темнее, а не всю картинку).
2. Экспозиция (усиление 2^Δ).
3. Градиентный ND (верх кадра теряет `gnd_stops`, мягкий переход по средней пятой, размыт диафрагмой).
4. Поляризатор: затемнение неба = степень поляризации Рэлея sin²γ/(1+cos²γ), максимум 75 %, × ясность неба, по углу
   каждого пикселя неба от солнца. Широкий угол даёт неровное небо, к солнцу эффекта нет.
5. Вспышка: обратные квадраты по карте глубины, применяется к цвету поверхности (пиксель / освещённость из сетки
   света). Если что-то движется, свет вспышки — отдельный слой.
6. **ГРИП и боке** (12.1).
7. **Смаз** (`MotionBlur`, 12.2) и вспышка как резкий слой в начале/конце выдержки.
8. Rolling shutter (12.3).
9. Сдвиг тилт-шифта, затем фишай-ремап или геометрия объектива (дисторсия k1, латеральная ХА, круг изображения).
10. `lens`: виньетирование, дифракция, мягкость углов.
11. Износ: запотевание, пыль, децентровка.
12. Блики (солнце в кадре или рядом).
13. Black Mist, звёздный фильтр.
14. Шум и горячие пиксели (12.5).
15. Отсечка на насыщении матрицы `rawSaturation(DR)`.

**`finish`** — процессор камеры: баланс белого на данных матрицы (выгоревшие пиксели делаются нейтральными, небо
остаётся белым; множители ≥ 1), мягкое «плечо» светов (колено 0.6–0.9 по ДД: больше ДД — длиннее плечо), цветовой
профиль (S-кривая контраста с закреплёнными концами, насыщенность, монохром, тинт, подъём теней). Classic Chrome
сделан селективным сдвигом оттенка, а не глобальным тинтом (белые остаются нейтральными).

**Запас RAW**: насыщение ≈ 1–1.3 EV выше белого JPEG (реальные RAW клипуют на 3–3.5 EV над средне-серым
независимо от матрицы); больший ДД даёт стопы в тенях (меньше шум чтения), а не в светах.

### 12.1 ГРИП и боке

- Круг рассеяния: `CoC = |A·f·(S−D)/(D·(S−f))|` с реальными f, N, дистанцией фокуса и размером матрицы; знак
  различает передний и задний план. CoC полного кадра 0.03 мм, масштабируется кроп-фактором.
- **Размытие слоями (`processing/LensBlur`)**: каждая точка расплывается в диск формы диафрагмы
  (`BokehKernel`: многоугольник по лепесткам или круг, профиль стиля боке; перед плоскостью фокуса диск перевёрнут).
  Кадр делится на слои по знаковому радиусу (шаг ×1.5, пиксель делит вес между двумя соседними слоями), слой
  сворачивается своим диском в уменьшенном разрешении (диск там ≤ 8 px), пустые тайлы пропускаются. Сборка сзади
  вперёд: дальние слои «over» друг на друга (закрывают по занятости пикселя), нормировка на покрытие (фон
  продолжается за объект, без тёмного ореола); резкий слой; ближние слои — от ближнего к фокусу к ближнему к
  объективу, каждый «over» на предыдущие без нормировки (полупрозрачные края; дым у объектива закрывает слегка
  размытую землю перед фокусом). Пиксель закрывает то, что за ним, только в своём дальнем слое из пары, иначе он
  закрывал бы собственную долю в соседнем. Дыры под передним планом заливаются сначала тем, что лежало под пикселем
  в ближних слоях за ним (земля за дымом; раньше, когда весь кадр перед фокусом, заливать было нечем — тёмная кайма
  и резкий край облака), затем pull-push (фон за травинкой). Предел радиуса 0.3
  ширины (600 мм f/4 на 5 м даёт диск больше половины кадра). К краям кадра диск каждого тайла обрезается
  «кошачьим глазом» (оправа виньетирует зрачок), у вихревого стиля ещё и сжимается вдоль радиуса — 16 направлений ×
  6 дистанций ядер на слой; гаснет за 2 ступени. В живом превью диск пока одинаковый по всему кадру.
- **Блики боке**: яркие точки извлекаются до размытия (их энергия вычитается из размываемой картинки) и рисуются
  диском формы диафрагмы: многоугольник по числу лепестков (скругление при открытой), «кошачий глаз» к краям. На
  открытой диафрагме диск круглый; кошачий глаз и вихрь пропадают при диафрагмировании. Маленькие яркие источники
  берут радиус окружения (нет резкой точки внутри диска).
- **Тилт**: дистанция фокуса своя для каждой строки (`Optics.tiltedFocusM`, Шаймпфлюг, шарнир J = f / sin tilt).
- **LoCA**: ГРИП считается дважды (зелёный против красного/синего радиуса): пурпурная кайма перед фокусом, зелёная
  за ним.
- **Макро**: ГРИП от расстояния объектив–объект (на 1:1 f/2.8 глубина 0.34 мм).
- **Сквозь воду, стекло и лёд** (`client/render/DepthLayers`, `processing/LayeredDepth`): на Fast/Fancy глубина
  копируется на GPU после block entities (непрозрачный мир) и после прозрачных блоков; на Fabulous берутся цели
  translucent/particles. Проверка `DepthUpsampler.agrees` идёт по полной глубине (лучи останавливаются на воде),
  затем: за поверхностью воды — видимая глубина `поверхность + d / 1.33` (кроме съёмки из-под воды), за цветным
  стеклом и льдом — глубина непрозрачного; тип поверхности даёт сетка лучей (`CameraRays`, 4-я сетка: жидкость /
  `HalfTransparentBlock`, стеклянные панели, маяк). Частицы (дым костра тоже) остаются на своей глубине. Дождь и
  снег на Fast/Fancy глубину не пишут — пока видоискателю или съёмке нужна глубина, `LevelRendererWeatherMixin`
  включает им запись глубины (после погоды уровень больше ничего не рисует, рука — после очистки глубины); на Fabulous
  берётся цель погоды (в ней только погода, ближняя глубина побеждает). Проверка GPU-глубины без шейдерпака идёт по
  `LayeredDepth.rayView` — тому, что видят лучи: непрозрачный мир плюс поверхность воды (лучи останавливаются на воде,
  проходят сквозь цветное стекло — у него пустая визуальная форма — и не видят частиц и дождя); `dropFixedLayer` —
  только со шейдерпаком: частицы — плоские билборды лицом к объективу, и облако дыма принималось за «фиксированный
  слой» пака, а вся глубина отклонялась в пользу сетки лучей. Рамка цветного стекла (его
  непрозрачные края) берёт глубину того, что за стеклом, и остаётся резкой. Со шейдерпаком — одна глубина, как раньше.
  Превью: те же копии, правило в `realcamera_dof_coc` без поправки на преломление (тип поверхности на GPU неизвестен).
- **Характер объектива** (`optics.character`, `BokehKernel.profile`, тот же профиль в превью):
  - сферическая аберрация: при недокоррекции (> 0) диски за фокусом с ярким центром и мягким краем, перед фокусом —
    с ярким ободком; гаснет за 2 ступени;
  - аподизация (STF): диск плавно темнеет к краю (гауссоподобно);
  - центральное экранирование (зеркальный объектив): тёмный центр диска, «бублик»; виден только у источников
    меньше дырки;
  - мягкий фокус (`soft`, Canon EF 135 Softfocus): свечение как у фильтра Black Mist (`ImagePipeline.mist`),
    гаснет за 2 ступени;
  - кривизна поля: плоскость резкости изгибается к объективу с квадратом высоты изображения
    (`Optics.curvedFocusM`, `ImagePipeline.curvedFocusM`, в превью — `rcFocusMm`); на меньшей матрице кривизна
    × q². Общая мягкость углов в `lens()` тогда уменьшена (кривизну не считаем дважды).
- **Диски бликов** нормируются по их фактическому профилю (энергия сохраняется при любом профиле); перед плоскостью
  фокуса многоугольник перевёрнут. Цветные каймы бликов дают две прогонки LoCA (у красного/синего свой радиус).

### 12.2 Смаз (`processing/MotionBlur`)

Кадр — **середина** экспозиции; каждая точка размазывается по пути своего изображения:

- весь кадр — остаточная тряска рук (правило 1/фокусное_экв, продлённое стабилизацией IBIS + OIS) как короткое
  случайное блуждание и панорамирование (поворот вправо двигает мир влево);
- движущаяся камера (лодка, вагонетка, лошадь) добавляет параллакс: ближнее летит быстрее дальнего;
- движущиеся сущности (`CameraRays.motionField`: маска по ячейкам, скорость, диапазон глубины бокса) — отдельные
  слои: фон под ними восстанавливается push-pull заливкой, сущность размазывается со своим покрытием (становится
  полупрозрачной там, где была часть времени) и кладётся сверху. **Проводка за бегущим животным оставляет его
  резким**, фон смазывается. Наездник и его скакун движутся с камерой — относительная скорость ноль.
- На длинных выдержках проводка, поездка и объекты записываются по-настоящему (накопление кадров), добавляется
  только тряска.
- В `ShotInfo` уходит смаз объекта AF.

### 12.3 Rolling shutter

Только электронный затвор: сдвиг строк пропорционально скорости поворота × `readout_ms`; наклоны камеры растягивают
или сжимают кадр по вертикали (`rollingSkewY`); движущиеся объекты наклоняются по своей скорости.

### 12.4 Оптика объектива

- Дисторсия k1 (линейно между концами зума) и латеральная ХА; в камере по умолчанию «коррекция объектива» убирает
  большую часть (как реальные камеры). Виньетирование, дисторсия и ХА масштабируются по диагонали матрицы / кругу
  изображения (полнокадровое стекло на кропе виньетирует меньше).
- Виньетирование падает при диафрагмировании, у широкоугольников остаётся остаточное (cos⁴).
- **Дифракция**: гауссиана на канал, σ = 0.42 λ N, λ = 600/530/460 нм.
- Мягкость углов на открытой диафрагме.
- **Блики**: вуаль, «призраки» по оси через центр, лучи звезды при диафрагмировании.

### 12.5 Шум

Модель переноса фотонов: σ(luma) = √(luma·shot + read²)·avg. Источники складываются в квадратуре:

- **Усиление = только ISO/100** (не недоэкспозиция): экспонирование «вправо» даёт чище картинку; переэкспозиция шум
  не добавляет.
- **Площадь матрицы**: меньшая матрица собирает меньше света при том же кадрировании (FF чище APS-C и MFT).
- **Шум чтения** ∝ 2^(13.5 − DR): матрица с большим ДД чище в тенях.
- **Цветовой шум** — доля на канал; **полосы по строкам** (больше на матрицах с низким ДД); уменьшение кадра
  усредняет шум (`resolutionScale`).
- **Тёмновой ток** удваивается каждые 6.5 °C (`SensorHeat`: температура воздуха биома, ночью холоднее, live view и
  длинные выдержки греют матрицу за минуты, OVF — гораздо меньше).
- **Горячие пиксели**: ≈ 1 на 100 000 пикселей матрицы, на фиксированных местах для конкретной камеры (сид — модель
  камеры игрока), яркость растёт с выдержкой, температурой и ISO, цвет по фильтру RGGB. Шумоподавление длинных
  выдержек вычитает тёмный кадр (и его шум считается дважды).
- Шум детерминирован сидом и считается последовательно.

### 12.6 Производительность

Строковые циклы (слои ГРИП, вихрь, смаз, rolling shutter, геометрия, сдвиг, фишай, виньетка, резкость,
блики) идут **параллельными стримами**; общие временные массивы внутри них запрещены (аллокация на строку).
sRGB-кодирование через таблицу на 65536 значений. Бенчмарк `PipelineBenchmarkTest` (3840 × 2560): портрет f/1.8
3.5 → 1.2 с, вихрь Гелиоса 5.5 → 1.4 с, фишай 2.8 → 0.8 с, пейзаж 2.3 → 0.7 с.

## 13. Спецоптика: фишай, тилт-шифт, макро, винтаж

### 13.1 Фишай

Игра не может отрендерить 180°. Рендерится прямолинейный кадр с ограниченным углом (полуугол в углу ≤ 74°,
`Optics.renderVfovDeg`), затем `ImagePipeline.fisheye` перемаппит его попиксельно в проекцию объектива (equisolid,
stereographic, equidistant). Центр сохраняет истинный масштаб (не сжимается). Круговые фишаи на полном кадре — чёрное
вне 180°. На фишаи фильтры не ставятся (резьба 0).

### 13.2 Тилт-шифт (Canon TS-E 24mm f/3.5L II)

Параметры `tilt`/`shift` (диски TILT/SHIFT появляются только на таком объективе).

- **Shift**: вид рендерится наклонённым вверх на atan(shift/f) и на 12 % шире, затем `lensShift` перепроецирует его на
  вертикальную матрицу — вертикали параллельны. Анализ кадра на сервере вычитает этот наклон.
- **Tilt**: дистанция фокуса по строкам (Шаймпфлюг). Обратный наклон — «игрушечный город».

### 13.3 Макро

`max_magnification` по каталогу (макро 1:1: Sony 90mm, Nikon MC 105mm, Canon RF 100mm, Fujifilm 80mm; зумы ≈ 1:3–1:5).
Видоискатель показывает масштаб от 1:10, кадр сужается с увеличением, растяжение теряет до 2 EV на 1:1 (TTL это
видит), ГРИП — доли миллиметра. Ограничение: на 1:1 кадр 36 мм — меньше одного текселя блока, макро показывает
тексели.

### 13.4 Винтажное боке

`swirl` (Гелиос-44-2: фон размазан по окружностям, диски сжаты в тангенциальные овалы), `bubble` (Trioplan: яркие
тонкие ободки «мыльных пузырей»), `busy` («луковые кольца»).

## 14. Аксессуары: вспышка, фильтры, ручка, штатив, сумка

### 14.1 Вспышка

Накамерные (Sony, Nikon, Canon, Fujifilm, Godox) и встроенные (`flash.built_in_gn` тушки). Режимы: выкл,
заполняющая, по второй шторке, авто (только в темноте); компенсация ±2 EV.

- **TTL-мощность** из ведущего числа, ISO, диафрагмы и дистанции фокуса; учитывает потери фильтра, объектива и
  растяжения.
- **Перезарядка** и расход батарей вспышки (полный импульс = 1 заряд).
- **Синхронизация**: на выдержках короче синхронизации вторая шторка затеняет нижнюю часть кадра, если нет HSS. HSS:
  ≈ 1.7 EV потери на входе, затем 1 EV на ступень; TTL поднимает мощность до полной. Центральный затвор
  синхронизируется на любой выдержке. С электронным затвором — только при считывании ≤ 8 мс.
- В снимке свет падает как 1/d² по карте глубины. Передняя/задняя шторка определяет, где резкий слой вспышки
  относительно смаза.
- Сервер ограничивает заявленное GN спецификацией и рассылает `FlashPop` (раздел 25.1).

### 14.2 Фильтры

Фильтр подходит, если его диаметр равен резьбе объектива, или через повышающее кольцо (`StepUpRingSpec`, issue #7):
вход кольца равен резьбе, диаметр фильтра ≥ выхода кольца (`FilterSpec.fits(thread, ring)`); на резьбу 0 (фишаи,
компакты) — нельзя. Резьба видна в подсказке объектива. Размеры 67/77/82/95/112 мм (не все виды во всех размерах),
всего 52. До 0.8.5 подразумевалось кольцо для любого фильтра ≥ резьбы, а самих колец не было.

Кольцо — отдельный предмет `step_up_ring` (15 штук: 39/40/43/46/49/52/55/58/60/62→67, 67→77, 72→77, 77→82,
82→95, 95→112), нового слота нет. Фильтр и кольцо свинчиваются в любой ячейке (`AccessoryItem.overrideOtherStackedOnMe`,
как мешок): ПКМ одним по другому, а в ячейке фильтра камеры — и ЛКМ, где обычный обмен был бы запрещён. Результат —
фильтр с компонентом `STEP_UP_RING`; оптика читает фильтр как раньше, кольцо влияет только на `fits`. Голое кольцо
тоже можно положить в ячейку фильтра (если подходит к резьбе) — затем накрутить на него фильтр; для оптики это
«без фильтра», при падении оно не трескается. ПКМ пустым курсором по фильтру на кольце разделяет их: в ячейке
остаётся та часть, которая в ней допустима (в инвентаре — фильтр, в камере — кольцо на объективе), другая уходит в
курсор; если ни одна не допустима, работает обычный клик. Снятый фильтр уносит кольцо в компоненте, ремонт
стекла (`repair_filter`) компоненты сохраняет.

| Вид | Действие | Потеря света |
|---|---|---|
| `nd` (ND8/64/1000) | −3/−6/−10 EV; экспонометр мерит через фильтр, ND1000 днём даёт длинные выдержки | по ступеням |
| `cpl` | поляризация неба по Рэлею (раздел 12) | 1.5 EV |
| `uv` | только защита: при падении трескается первым | 0 |
| `color` | пропускание по каналам: жёлтый, оранжевый, красный, зелёный для ч/б; 80A (синий), 85 (янтарный) | 1 EV или своё |
| `mist` | Black Mist 1/8, 1/4: свечение вокруг светлого, подъём теней | 0 |
| `gnd` | GND8: затемняет верхнюю половину | 0 (по замеру) |
| `star` | 6 лучей от ярких точечных источников (фонари, звёзды), до нескольких сотен самых ярких | 0 |

### 14.3 Батарейная ручка

Вторая батарея на перечисленных тушках; расходуется первой. Ручки, батареи и вспышки заряжаются в зарядном
устройстве.

### 14.4 Штатив (`entity/TripodEntity`, `client/camera/TripodView`)

Ставится на землю. ПКМ камерой — закрепить (на сущности хранится копия камеры, синхронизируется клиентам), ПКМ
пустой рукой — смотреть через камеру, Shift + ПКМ — забрать камеру, удар — сложить (камера выпадает).

- Вид поворачивается мышью **каждый кадр** (`ComputeCameraAngles`), а не по повороту сущности (20 раз в секунду и
  перезаписывается эхом сервера). Пакет `TripodAim` отправляется только при изменении.
- Тряски нет, ходьба заблокирована, Shift — отойти. Клавиши камеры работают.
- Фотограф не рисуется в своём видоискателе; таймер продолжает идти после того, как он отошёл, а захват рендерится
  со штатива — можно попасть в кадр самому.
- Модель (`client/render/TripodRenderer`) наклоняет камеру по `xRot` сущности, как вид и снимок: наклон в Minecraft
  положителен вниз, а объектив в позе головки смотрит в −z, поэтому поворот вокруг +x берётся с минусом (иначе
  камера, наведённая в небо, со стороны смотрит в землю — issue #11). Автотест `stage3` снимает голову, задранную
  вверх и опущенную вниз: вид, фото и модель сбоку (`s3_07b_*`, `s3_07c_*`).

### 14.5 Сумка и набор для чистки

Сумка: 12 ячеек только для фототехники. Набор для чистки (камера во второй руке): убирает пыль с матрицы и сушит.

## 15. Износ и ремонт

`gameplay/WearEvents`, `component/CameraWear`.

- **Затвор**: механический/EFCS спуск увеличивает счётчик. Ресурс — среднее: ≈ 5 % затворов отказывают раньше, шанс
  растёт к ресурсу и быстро после него. Заклинивший затвор блокирует любой спуск.
- **Влага** (раз в секунду): дождь (камера в руке) и вода (где угодно в инвентаре) по защите от непогоды; > 40 —
  запотевание оптики («мыльный» кадр), 100 — мёртвая электроника у незащищённых. Защита 2 тоже тонет, только
  медленнее. Вне воды камера сохнет.
- **Падения** ≥ 4 урона с камерой в руке: сначала трескается UV-фильтр, иначе объектив получает децентровку (одна
  сторона кадра мягкая). Встроенный объектив компакта не сбивается.
- **Пыль**: смена объектива в пустыне, бесплодных землях, Незере, на пляже или под дождём может посадить пятно
  (позиция + радиус); видно примерно с f/8.
- **Холод**: снежные биомы и высокогорье — батареи ×1.5 быстрее.
- **Ремонт** в фотомастерской (`repair`-рецепты сохраняют компоненты предмета): затворный блок (сбрасывает счётчик),
  электроника, объектив, фильтр. Пыль и влагу убирает набор для чистки.

## 16. Файлы: JPEG, EXIF, RAW

- **Автоэкспорт** (конфиг `autoExport`, вкл): каждый снимок — полноразмерный JPEG в
  `screenshots/realcamera/<дата>/DSC0NNNN.JPG`, как папка карты камеры.
- **EXIF** (`processing/ExifWriter`, собственный минимальный писатель APP1, little-endian TIFF, IFD0 + Exif sub-IFD):
  Make, Model, Orientation, Software, DateTime, Artist, ExposureTime, FNumber, ExposureProgram, ISO, ExifVersion,
  DateTimeOriginal, ExposureBias, MeteringMode, Flash, FocalLength, размеры, WhiteBalance, FocalLengthIn35mmFilm,
  LensMake, LensModel. В Lightroom снимок выглядит снятым настоящей камерой.
- **RAW** (`processing/RawFile`): результат `developSensor` (до коррекций объектива и `finish`) как **16-битный
  линейный PNG** (65535 = насыщение матрицы) + JSON-сайдкар: уровень белого, ББ и профиль «как снято», список
  профилей камеры, запечённые виньетирование/дисторсия/ХА для коррекции профиля в редакторе. В обычном просмотрщике
  выглядит тёмным и плоским, как непроявленный RAW. RAW без коррекций объектива. Сайдкары этапа 2 (без `version`)
  читаются как 8-битные sRGB-кадры.
- **Размер на карте** реалистичный: JPEG Fine ≈ 0.35–0.5 МБ/МП, сжатый RAW ≈ 1.2 МБ/МП. Игровая копия всегда
  маленький JPEG.
- `client/photo/LocalOriginals` (`realcamera_cache/originals.json`) помнит, какие локальные файлы принадлежат какому
  id снимка, — автор редактирует полноразмерный оригинал.
- Debug: `realcamera.debugDumps` пишет `raw_<ms>.jpg` / `depth_<ms>.jpg` в `screenshots/realcamera_debug/`.

## 17. Сервер: хранилище, карты, сеть, квоты

### 17.1 Хранилище (`photo/`)

- Файлы: `<мир>/realcamera/photos/<2 символа>/<uuid>.jpg`.
- `PhotoIndex` (SavedData `realcamera_photos`): UUID → `PhotoMeta` (автор, время, тушка, объектив, EXIF, биом,
  измерение, координаты, анализ кадра), размер файла, размер на карте, `latent` (скрытый плёночный кадр), рейтинг
  0–5, загрузивший (платит квотой за правку чужого снимка), персональные квоты.
- `CardStorage` (`realcamera_cards`): UUID карты → список снимков. Сам предмет хранит только UUID и зеркало занятого
  места (иначе NBT раздуется).
- **Удаление файла** только когда ни одна карта на него не ссылается и он ни разу не печатался
  (`ServerPhotoService.removeFromCard`). Форматирование карты B не удаляет общий с картой A файл.
- Разбор JPEG только по заголовку (`PhotoStorage`), пиксели не декодируются — защита от «бомб».

### 17.2 Сеть (`network/Payloads`, `RCNetwork`)

`CustomPacketPayload` + `StreamCodec`. Клиент → сервер куски ≤ 30 000 байт (ванильный лимит 32 КиБ), сервер →
клиент по 256 КиБ.

Клиент → сервер: `UpdateSettings`, `Shutter` (тип затвора, реальное GN вспышки, `ShotInfo`), `UploadBegin` /
`UploadChunk`, `RequestPhoto`, `RequestCard`, `DeletePhoto`, `TripodAim`, `RewindFilm`, `EditUploadBegin`,
`ComputerAction` (удалить, рейтинг, копировать/перенести, форматировать), `AlbumAction` (вставить, взять, подпись).

Сервер → клиент: `UploadStatus`, `PhotoData`, `PhotoGone` (заглушка после удаления админом), `ViewPhoto`,
`CardContents`, `OpenLecternAlbum`, `FlashPop`, `NeckCamera`, `JournalSync`.

### 17.3 Поток снимка

1. ЛКМ → клиент шлёт `Shutter`: сервер снимает заряд, считает срабатывание (механический/EFCS), проигрывает звук
   окружающим, проверяет вспышку и рассылает `FlashPop`, запускает анализ кадра (`ShotInfo.nonce`).
2. После проявки `PhotoUploader` (последовательная очередь: серия стоит за записываемым кадром, как буфер карты)
   шлёт `UploadBegin` (мета, размер, качество/формат для учёта места на карте) → сервер проверяет квоту, rate-limit,
   карту → `UploadStatus` → куски → проверка заголовка JPEG и размеров → файл, индекс, карта, анализ по nonce →
   `PhotoEvents.photoStored`.
3. Плёночные кадры загружаются как **латентные** под id ролика; не видны, не скачиваются, не экспортируются на диск,
   клиент не кэширует их (сервер изменит их при проявке).
4. Загрузка правки с компьютера (`EditUploadBegin`) — новый снимок на карту в том же компьютере.
5. Скачивание (`RequestPhoto`) идёт с бюджетом трафика на игрока по серверным тикам.

Тяжёлые операции (запись файлов, проявка, увеличитель) — в `Util.ioPool()`, в главный поток возвращаются только
результаты. Доступ к карте проверяется (`canAccessCard`: карта в руке, в камере, в машине рядом).

### 17.4 Квоты и приватность

`serverconfig/realcamera-server.toml`: снимков на игрока 500, хранилища 200 МБ, сторона игровой копии 1280 px, файл
800 КБ, загрузок в минуту 120, `storeRawOnServer` (выкл), `showCoordinatesToOthers` (выкл — координаты видит только
автор, `visibleMeta`). Персональные квоты — `/photo quota`.

## 18. Клиентский показ снимков

`client/photo/PhotoCache`: GL-текстуры в LRU с бюджетом VRAM (`textureCacheMb`, по умолчанию 256), дисковый кэш
`realcamera_cache/<хэш адреса сервера или мира>/<uuid>.jpg`, загрузка по запросу. Всё, что показывает снимок,
каждый кадр спрашивает `texture(UUID)`; невидимые несколько секунд текстуры вытесняются. Свежий снимок кладётся в
кэш сразу (без круга через сервер). `PhotoGone` → заглушка «удалено». При отключении память очищается, диск остаётся.

Рендереры: отпечаток в руке (`PrintItemRenderer`, BEWLR), рамки на стене (`PhotoFrameRenderer`), настольная рамка и
стенд (`DisplayRenderer`), экраны просмотра, принтера, компьютера, альбома.

## 19. Блоки-устройства

Общая основа: `MachineBlock` (горизонтальная ориентация, открывает меню) + `MachineBlockEntity` (сохраняемый
инвентарь, выпадает при разрушении). **Меню не зависят от клиентского block entity**: пакет открытия экрана может
прийти раньше обновления блока. Машины читают карту через `CameraHelper.slotCard`: карта сама или карта внутри

## 20. Компьютер и редактор

### 20.1 Компьютер (`ComputerBlockEntity`, `ComputerScreen`)

Два слота карт A/B (SD всегда, CFexpress только с апгрейдом-картридером), слот апгрейда (картридер или сканер
плёнки). Каталог миниатюр, рейтинг 0–5 звёзд, удаление, копирование/перенос на другую карту, форматирование
(двойное нажатие). Любая цифровая камера с картой — как USB. Со сканером проявленные плёнки в слотах можно листать,
оценивать, копировать на карту (скан) и править (результат на карту в другом слоте); удалять и добавлять кадры на
плёнку нельзя.

### 20.2 Редактор (`processing/PhotoEditor`, `EditSettings`, `client/editor/EditSession`, `EditorScreen`)

Чистая Java, в линейном свете. Порядок: коррекция профиля объектива → геометрия (поворот 90°, выравнивание с
автозумом без пустых углов, кадрирование с пропорциями) → экспозиция и ББ → «доводка» RAW (плечо светов + профиль
камеры) → тон (чёрные, белые, тени, света, контраст, кривая) → цвет (HSL в 8 полосах с треугольными весами,
сочность, насыщенность, ч/б) → детали (шумоподавление: края сохраняются по яркости, цвет сильнее; резкость) →
эффекты (виньетка, зерно).

- **RAW против JPEG**: RAW — данные матрицы до ББ и профиля с запасом над белым, поэтому экспозиция ±4 EV
  восстанавливает пересвеченное небо. JPEG уже готов: ±1.5 EV, выгоревшее остаётся выгоревшим. RAW при настройках по
  умолчанию = JPEG из камеры (юнит-тест).
- Температура/оттенок: ±100 ≈ ±2000 K вокруг дневного света. Кривая — монотонный кубический сплайн
  (Fritsch–Carlson) через 5 точек.
- Отмена/повтор, до/после (`\`), гистограмма, пресеты в `config/realcamera/presets`.
- Превью рендерится в рабочем потоке; каждое обновление — новая текстура.
- Автор правит полноразмерный оригинал со своего диска (`LocalOriginals`), остальные — игровую копию.
- «Сохранить копию» — новый снимок на ту же карту (`PhotoMeta.editedFrom`, квота загрузившего); «Экспорт на ПК» —
  полноразмерный JPEG с EXIF в `screenshots/realcamera/export/`.

### 20.3 Сдвиг фокуса и склейка (`Viewfinder.fireShift`, `processing/FocusStack`, `client/editor/StackJob`)

- Настройки `focusShots` (0 = выкл.) и `focusStep` (1–10) в третьей группе кодеков `CameraSettings`
  (`gen_settings.py` режет поля на группы по ≤ 16 и вкладывает `mapPair`; JSON остаётся плоским). Только цифровые.
- Одно нажатие спуска — серия на скорости CH (с учётом буфера и карты): шаги равны в диоптриях, Δ(1/d) =
  шаг × 0.2 / H (шаг 5 = половина ГРИП); до ∞ серия обрывается. Фокус на время серии ведёт она (не AF и не кольцо),
  потом возвращается. HUD: «FS 3/10».
- Компьютер: Shift+клик отмечает кадры, «Стек (N)» (до 20 кадров). Кадры открываются как в редакторе
  (`EditSession`: оригинал автора или игровая копия), проявляются настройками по умолчанию, при разном размере
  уменьшаются до меньшего. `FocusStack.align`: масштаб вокруг центра (дыхание) и сдвиг, перебор грубо → точно на
  уменьшенной яркости (√L), MSE по середине кадра. `Fuser`: пирамиды Лапласа, на каждом уровне выигрывает кадр с
  наибольшей локальной деталью (|L| яркости, среднее 3×3), основание — среднее; кадры добавляются по одному.
  Результат — новый снимок (`editedFrom` = первый кадр), полноразмерный файл в `realcamera_cache/edits/`.

## 21. Плёнка и фотолаборатория

### 21.1 Плёнки (`FilmStockSpec`)

Девять: Portra 400, Ektar 100, Gold 200, Tri-X 400, HP5 Plus 400, Delta 3200, Velvia 50, Provia 100F,
CineStill 800T. Поля: процесс (`c41`/`e6`/`bw`), ISO коробки, кадров (135: 36, 120: 12), латитуда вверх/вниз,
«вид» (контраст, насыщенность, тинт, подъём теней), зерно (сила, размер на скане 2560 px, халация), показатель
Шварцшильда, цветовой дрейф длинных выдержек.

- **Латитуда**: негатив печатается «обратно к норме» — переэкспозиция в пределах латитуды почти не видна (×0.15),
  недоэкспозиция печатается жидкой (×0.35), за пределами ошибка видна целиком. Слайд показывает любую ошибку.
  Допуск оценки звёзд — по плёнке.
- **Невзаимозаместимость**: после 1 с плёнка ведёт себя как при t^p, теряет (1−p)·log2 t EV (Tri-X ≈ 0.6: замер 10 с
  требует ≈ 50 с; современный цвет ≈ 0.9). Цветной дрейф: большинство в зелень (Velvia), Provia — нет; негатив частично
  корректируется печатью; ч/б — нет.
- **Зерно** на грубой сетке, сильнее в средних тонах и при недоэкспозиции; средний формат мельче. **Халация** у
  CineStill (нет противоореольного слоя): красно-оранжевое свечение вокруг огней; CineStill с синим тинтом.
- Плёнка сбалансирована на дневной свет (тунгстен у «T»), авто-ББ нет.

### 21.2 Плёночные камеры и ролик (`FilmRoll`)

Состояния: свежий, заряжен, экспонирован (перемотан), проявлен, испорчен. Ролик вставляется в слот карты. ISO
задаёт камера по своему `iso_dial` (`Viewfinder.effectiveIsoIndex`): `manual` — диск ASA/ISO без автомата, пока
не тронут, стоит на коробке, выставленное значение не сбрасывается при смене ролика (как в жизни: надо помнить,
какая плёнка заряжена); `dx_override` (EOS-1V) — DX-код, можно перебить; `dx` (Contax T2) — только DX, параметр
не выбирается; `none` (Hasselblad 500C/M, без экспонометра) — параметра нет, плёнка экспонируется по коробке.
Диапазон — от −1 до +3 ступеней от коробки, чтобы потом сделать пуш/пул; HUD показывает отклонение («ISO 1600
+2.0»). Экрана нет: кадры видны
только после проявки. Перемотка — меню G. Неперемотанный ролик, вынутый на свету > 3, засвечивается
(`CameraPartsMenu.openBack`): последние кадры выжжены, на остальных полосы, затухающие к началу (у ч/б нейтральные).
Плёнку 120 перематывать не нужно. Hasselblad 500C/M — кадр 6×6.

### 21.3 Проявочный бак

Перемотанный ролик + химия своего процесса (C-41 / E-6 / ч/б, 8 роликов на набор), пуш/пул −1…+2, ≈ 1 минута (1200
тиков). Загрузка катушки требует **темноты** (без красного фонаря рядом — плёнка панхроматична) или **зарядного
рукава** в слоте; иначе испорчен весь ролик. Ролик остаётся в закрытом баке до конца; если открыть бак посередине —
засветка. На сервере `FilmLab.developRoll` перерисовывает каждый кадр (пуш: ярче, контрастнее, зернистее; пул —
мягче; протечки) и делает кадры видимыми; счётчик `film_developed` засчитывается по окончании. Правый клик по
проявленной плёнке — контактный лист.

### 21.4 Тёмная комната (`gameplay/Darkroom`)

В Minecraft свет не цветной, поэтому красный фонарь отличают сканированием источников: дневной свет и все лампы,
кроме фонаря, должны быть ниже уровня 4. Для плёнки фонарь тоже считается. Проверка кэшируется на секунду для меню.

### 21.5 Увеличитель

Проявленная плёнка + тёмная бумага (RC ч/б, баритовая ч/б, цветная RA-4) + химия для бумаги (ч/б; для RA-4 — цветная
C-41). Выбор кадра, экспозиция ±2 EV полуступенями, градация контраста 0–5 (ч/б), экспонирование 60 тиков. Бумага
засвечивается, если до неё доходит что-то кроме света фонаря; RA-4 нужна полная темнота. Слайд на негативной бумаге
печатается негативом. Отпечаток — новый хранимый снимок, производный от кадра (`FilmLab.enlarge`); засвеченные и
негативные отпечатки теряют анализ кадра.

## 22. Показ отпечатков: рамки, альбом, стенды

- **Отпечаток** (`photo_print`): рисует сам снимок (BEWLR), ПКМ — полноэкранный просмотр; подсказка показывает
  звёзды и что в кадре.
- **Рамка на стене** (`PhotoFrameEntity`): 1×1, 2×1, 1×2, 2×2, 3×2, 2×3, 4×3, 3×4; материалы дуб, ель, тёмный дуб,
  берёза, вишня, бамбук, чёрный металл, золото. Размещение и бокс как у картин. ПКМ отпечатком — вставить, Shift +
  ПКМ — паспарту (нет/белое/чёрное), удар по заполненной — вынуть отпечаток. Размер рамки ограничен бумагой отпечатка
  (`PaperData.maxFrameSide/fitsFrame`, правила в одном месте): 10×15 и A5 — только 1×1, A4 — обе стороны ≤ 2 блоков,
  A3 и отпечатки без известного размера — любая рамка. Неподходящий отпечаток не вставляется, игрок видит в строке
  действия, какая бумага нужна (`PaperData.smallestFor`); подсказки отпечатка («рамка на стене: до N×N») и рамки
  («нужен отпечаток на A4 или крупнее») говорят то же. Рамки не растут и не сливаются, поэтому проверяется только
  вставка; уже висящие отпечатки не трогаются. Настольную рамку, фотостенд и альбом размер бумаги не ограничивает.
- **Настольная рамка** и **фотостенд** (мольберт в два блока, держит нижняя половина): общие `DisplayBlock` /
  `DisplayBlockEntity` (отпечаток синхронизируется), горизонтальные/вертикальные по отпечатку. ПКМ отпечатком —
  вставить, пустой рукой — посмотреть, Shift + ПКМ — забрать. Настольная рамка, как голова моба, ставится в 16
  направлений (`FACING` — четверть, `TURN` 0..3 — ещё по 22,5° по часовой): модели блока в blockstate
  поворачиваются только на 90°, поэтому у повёрнутой рамки модель пустая (`table_frame_turned`), а саму рамку под
  своим углом рисует `DisplayRenderer` (`renderSingleBlock` модели с `TURN=0`).
- **Фотоальбом**: 48 отпечатков с подписями, вставка из второй руки или инвентаря. На кафедре (тег
  `minecraft:lectern_books`): ПКМ по кафедре перехватывается на сервере и открывает альбом только для чтения с кнопкой
  «взять».
- В творческом режиме вставленный отпечаток не расходуется (ванильное правило).

## 23. Игровые цели

### 23.1 Серверный анализ кадра (`analysis/FrameAnalyzer`)

При спуске клиент шлёт `ShotInfo` (nonce, фокусное, диафрагма, выдержка, ISO, дистанция фокуса, ошибка экспозиции,
смаз). Сервер **сам** по своему состоянию мира определяет: глаз и поворот фотографа или штатива (минус наклон
сдвига), поле зрения объектива; живых существ, чей бокс в кадре и видим (лучи к пяти точкам), их долю кадра,
дистанцию, центр, попадание в ГРИП; молнию; долю неба (96 лучей); солнце/луну в кадре; время, погоду, фазу луны;
структуру в точке фокуса; биом **в точке фокуса** (не где стоит фотограф); как снято (флаги: штатив, плёнка,
вспышка, электронный затвор, фишай, тилт-шифт, адаптер, средний формат, под водой); увеличение.

Явления: восход, закат (низкое солнце в соответствующее время), звёздная ночь, звёздные треки (ночь, небо ≥ 20 %,
штатив, выдержка ≥ 15 с — дописываются при загрузке по реальной длительности), полнолуние, дождь, гроза, снегопад,
молния (в том числе ударившая во время открытого затвора, `lightningStruck`), небо Энда, под водой.

**Защита от подделки**: заявленные настройки ограничиваются возможностями камеры и объектива, вспышка проверяется.
Ошибка экспозиции и смаз — измерения клиента (ограничены; модифицированный клиент мог бы улучшить звёзды, это
задокументировано). Телевик засчитывает существ только в пределах дальности прорисовки сущностей клиента.

Анализ ждёт загрузку по nonce и сохраняется в `PhotoMeta.analysis`; правки и отпечатки увеличителя его сохраняют.

### 23.2 Оценка (`analysis/QualityScore`)

0–100: экспозиция 25, резкость 25 (нерезкий объект теряет большую часть), размер объекта 25, правило третей 15
(центр тоже приемлем для портрета), шум 10. Объектом считается существо ≥ 2 % кадра. Без объекта — пейзаж: небо и
явления вместо размера и композиции, и пейзаж должен быть в фокусе. ≥ 75 → ★★★, ≥ 50 → ★★, иначе ★. Смазанный
главный объект — не выше ★★.

### 23.3 Фотоэнциклопедия (`gameplay/Journal`, `JournalScreen`)

Клавиша J или предмет «Полевой журнал». Attachment игрока, переживает смерть, синхронизируется `JournalSync`.
Вкладки: существа (все не-MISC типы сущностей плюс жители, големы, боссы, в том числе модовые), биомы (реестр
биомов), измерения (сервер присылает список), явления. Страница открывается первым **резким** снимком и хранит
лучший (миниатюра, звёзды, качество, игровой день); чат сообщает о новых страницах. Плёночные кадры считаются при
проявке, правки и чужие снимки — нет. Если ролик проявили, пока автор офлайн, зачёт придёт при входе
(`PendingCredits`).

### 23.4 Достижения (`gameplay/RCTriggers`, `tools/gen_advancements.py`)

Триггеры: `realcamera:photo_taken` (существо, звёзды, явление, биом, измерение, флаг, пределы выдержки, дистанции,
диафрагмы, увеличения, неба) и `realcamera:event` (prints, frames_hung, film_developed, edits, commissions,
commission_tier, shutter_count, journal_creatures/biomes/phenomena). 37 достижений в своей вкладке, например:
«Тихо, Варден» (Варден на 3★ электронным затвором), «Звёздный путь» (треки со штатива от 15 с), «Длиннофокусник»
(резкий объект дальше 150 блоков), «Глаза в глаза» (пчела от 1:2), «Механический» (100 000 срабатываний),
«Весь мир в объективе» (40 биомов), «Охотник за драконом».

### 23.5 Редактор газеты (`gameplay/NewspaperEditor`)

Профессия жителя с местом работы «Редакционный стол» (POI, тег job site, текстура одежды). Технику не продаёт;
покупает бумагу и выставляет **заказы на снимки** по уровням 1–5 (корова… → панда в бамбуковых джунглях, закат… →
Варден, Эндер-дракон, молния, звёздные треки), оплата изумрудами (от 2–4 до 36–56).

Реализация: заказ — компонент `realcamera:commission` на предмете-цене сделки; `ItemCostMixin` заставляет
`ItemCost#test` принимать любой отпечаток, чей анализ выполняет заказ (и для сделки, и для автозаполнения экрана);
`MerchantContainerMixin` / `MerchantResultSlotMixin` сообщают проверке продавца и запоминают проданные снимки
(`SoldPhotos`, по исходному кадру). Правила: только свои снимки, каждый кадр продаётся один раз (перепечатки,
увеличения и правки того же кадра не пройдут), отпечаток без чернил или засвеченный не принимается.

## 24. Получение техники: мастерская, рецепты, лут

- **Фотомастерская** крафтится на обычном верстаке. Рецепты `realcamera:assembly` (`AssemblyRecipe`): бесформенный
  список ингредиентов с количествами, результат с data-компонентами (какая модель), время сборки; жадное
  распределение по 6 слотам. `repair` = `shutter`/`electronics`/`lens`/`filter` делает результат отремонтированной
  копией входного предмета с его компонентами.
- **Выбор рецепта.** Многие рецепты совпадают по ингредиентам (все повышающие кольца, размеры фильтров одного вида,
  тушки одного тира), а входы могут содержать лишнее. `recipe/AssemblyChoices.find` даёт все подходящие рецепты в
  общем для сервера и клиента порядке: больше расходуемых предметов — раньше, затем по id. Станция запускает
  выбранный игроком (id хранится в NBT `recipe` и возвращается, когда входы снова ему подходят), иначе первый.
  Меню синхронизирует число вариантов и индекс текущего (`ContainerData` 2..3); экран сам строит тот же список по
  слотам и показывает ряд результатов (7 ячеек со стрелками), клик идёт через `clickMenuButton(index)`. Автотест
  stage1: самородки + краситель, выбор третьего варианта.
- Рецепты генерирует `tools/gen_recipes.py` из tier/kind каталога (сейчас 376 файлов рецептов, вместе с

## 25. Мультиплеер: вспышки, поза, камера на ремне

### 25.1 Чужая вспышка

Пакет `Shutter` несёт GN, который вспышка реально дала (мощность TTL). Сервер ограничивает его спецификацией и шлёт
`FlashPop` (позиция над объективом, ось объектива, GN) игрокам в радиусе 160 блоков, включая фотографа.

`client/render/FlashGlow`: импульс длится миллисекунду, но глаз интегрирует ≈ 0.1 с, поэтому видимая яркость —
добавленный свет относительно уже имеющегося (EV окружения): GN 36 в 10 м освещает лунную ночь как день и почти
незаметна на солнце. Свет идёт конусом по оси (полный внутри ~30°, исчезает к ~60°, немного рассеяния) и
перекрывается лучами (не проходит сквозь стены). Эффекты: мультипликативное осветление сцены, блик источника,
цветное послеизображение, которое двигается со взглядом; сила и длительность (от искорки до ~8 с) растут со
ступенями над адаптацией глаза. Рисуется на `RenderGuiEvent.Pre` — шейдерпак не важен. Свою вспышку фотограф тоже
видит, но только как осветление сцены — без блика источника и послеизображения (и с руки, и со штатива; issue #9);
импульсы во время захвата кадра откладываются, чтобы не попасть в снимок.

Если у игрока в этот момент открыт затвор, `PhotoCapture.remoteFlash` добавляет чужую вспышку в его кадр как
попиксельную сетку света с тенями и спадом по расстоянию (`ImageParams.Extras.otherFlash`).

### 25.2 Как держат камеру

- **Третье лицо**: `CameraItemExtensions` возвращает двуручную позу `CameraPose.ARM_POSE` (добавлена в
  `HumanoidModel.ArmPose` через `META-INF/enumextensions.json`): обе руки у лица, локти в стороны, вслед за головой.
  `SpecItemModels.Composite.applyTransform` поворачивает камеру обратно, пока рисуется поднятая камера
  (`CameraPose.raisedNow` выставляется в `RenderPlayerEvent`).
- **Камера на ремне**: камера в инвентаре, но не в руке, висит на груди. Чужие инвентари клиентам не отправляются,
  поэтому `gameplay/NeckCameras` шлёт `NeckCamera` (только то, что нужно модели: тушка и части) отслеживающим игрокам
  и самому игроку при изменении; рисует `NeckCameraLayer`. Камера висит объективом вперёд, задней стенкой к груди
  (поверх брони: нагрудник +1 px, поножи +0,5 px). Слой рисует составную модель с `ItemDisplayContext.NONE` (без
  дисплей-трансформов предмета) и ставит её по габаритам всех проходов (тушка + адаптер/телеконвертер/объектив вдоль
  оптической оси, кэш по модели): задняя грань тушки у груди, весь объектив снаружи при любой длине. Наклон — 8°
  объективом вниз вокруг нижнего края задней стенки; при приседании (наклон тела `body.xRot`) камера поворачивается
  обратно вокруг верхнего края, то есть отвисает от груди, и ни одна точка не уходит в тело. Проверка:
  `-Pautotest=pose`, скриншоты `strap_*.png` (китовый 28-70 и Z9 + TC-2.0x + 600 мм спереди, сбоку, в три четверти,
  сзади, присев и в нагруднике).

## 26. Совместимость

### 26.1 Iris и шейдерпаки (`client/render/ShaderCompat`, через рефлексию Iris API)

Мод подстраивается под любой пак, не только под Complementary:

- **Пак активен** и **теневой проход**: обработчики стадий уровня пропускают shadow pass (это не вид игрока).
- **Доверие к буферу глубины**: каждые 40 кадров буфер в сетке 5 × 4 сравнивается с лучами, плюс проверка полной карты
  снимка (`DepthUpsampler.agrees`, весит больше). Проба терпима к траве перед землёй (иначе размытие мигало при
  смене прицела), но ловит слой одной глубины. Пока недоверие — живой ГРИП выключен, снимок берёт сетку лучей.
- **`packRelight`**: паки по-разному рисуют ночь, у них своя автоэкспозиция и тонмаппинг. Снимок осветляется по тому,
  что пак реально нарисовал в замеренной области (лог-среднее по поверхностям, не по небу), против отражательной
  способности этих поверхностей, в пределах ±3 EV вокруг ванильной кривой.
- Всё переизучается при смене пака.
- **Окно не ресайзится** при захвате с паком (раздел 11).
- **`IrisCenterDepthMixin`** (`@Pseudo`): пока камера поднята, `centerDepthSmooth` Iris (глубина под прицелом, на
  которую пак фокусирует свой ГРИП) перезаписывается дистанцией фокуса объектива через проекцию уровня — ГРИП пака
  фокусируется туда же, куда объектив. Если у пака свой ГРИП, лучше выключить один из двух.

### 26.2 Просмотрщики рецептов (`client/compat/`)

Плагины JEI, EMI и REI компилируются против API (`compileOnly`) и загружаются только самим просмотрщиком
(`@JeiPlugin`, `@EmiEntrypoint`, `@REIPluginClient`) — без них мод работает. Три категории из общих данных
`RecipeViews`: фотомастерская (все рецепты с количествами, временем, пометкой ремонта), проявка (экспонированный ролик
каждой плёнки + её химия → проявленный; бак и рукав как рабочие станции), увеличитель (проявленный ролик + каждая
бумага → отпечаток). Каталожные предметы различаются по компоненту модели (JEI subtype interpreter, EMI comparison,
REI comparator). Синтетические id рецептов начинаются с `/` (конвенция EMI).

## 27. Модели, текстуры, звуки (генераторы)

Все ассеты генерирует `tools/gen_assets.py` (текстуры, модели предметов/блоков, blockstates, звуки `.ogg` через
ffmpeg); выход перезаписывается, править нужно генератор.

- **Ограничения формата Minecraft**: элементы в пределах −16..32, поворот только ±22.5/45° по одной оси. Поэтому
  `cylinder()` строит правильную 16-гранную призму из 8 повёрнутых «спиц» (текстура боковой стороны оборачивается
  16 полосами) — объективы, байонеты, адаптеры круглые. Очень длинные объективы укорочены до 24.5 единиц; кольцевые
  ступени между цилиндрами разных радиусов закрыты (были сквозными).
- **Стили тушек**: плоская (α6400), ретро (Zf/X-T5), ретро-SLR (AE-1/FM2), компакт (X100VI/Q3/T2), про со встроенной
  ручкой (Z9/R1), большой средний формат (GFX/X2D), «коробка» Hasselblad V.
- **Отделки объективов** (`LENS_LOOKS`): красное кольцо Canon L, белые телевики, Sony GM, Nikon S, хромовый винтаж с
  кольцом диафрагмы, кольцо диафрагмы Fujifilm, титан; фишай — выпуклая линза с лепестковой блендой.
- **Составная модель** (`client/render/SpecItemModels`): в 1.21.1 ещё нет item model definitions, поэтому модель
  выбирается по компоненту (имя модели в JSON спецификации), а камера рисуется несколькими проходами: тушка +
  `_mounted`-модели адаптера/ТК/объектива, сдвинутые вдоль оптической оси на длину стоящих сзади частей (1 единица
  модели ≈ 9 мм, общая точка байонета). `BakedModelWrapper.applyTransform` по умолчанию возвращает внутреннюю модель
  и теряет проходы — композиты переопределяют его на `this`.
- Длинные объективы уменьшены в инвентаре, мелкие детали (адаптеры, блинчики) увеличены в слотах и рамках; рамки
  предметов показывают камеру спереди.
- Звуки синтезированы: шторки беззеркалки, зеркало, тихий центральный затвор, перемотка и т. д.

## 31. Известные ограничения и сознательные отказы

- **Пересвет глобальный**: нет попиксельного контраста тень/солнце при замере по тени (сетка света грубая, были бы
  ореолы).
- **Лучи не видят** траву/цветы/листву без коллизии и реальную форму мобов (только боксы). Основная карта глубины —
  буфер GPU; только в фолбэке (сетка лучей) остаются старые артефакты: трава размыта как земля за ней, резкий ореол
  вокруг портретов на открытой диафрагме. С некоторыми паками ночью глубина GPU непригодна — используется сетка.
- **Видимость и размер существ в анализе** считаются по боксам.
- **Макро 1:1** показывает один-два текселя Minecraft-пчелы.
- **Видоискатель сдвинутого объектива** показывает наклонённый (сходящийся) вид; выпрямлен только снимок.
- **Скорость серии** ограничена рендером в разрешении матрицы (~3 кадр/с на iGPU с шейдерами).
- **С шейдерпаком** снимок в разрешении окна (кроп под аспект), а не матрицы.
- **Байеровская мозаика / муар — отказ**: снимок рендерится ниже разрешения матрицы (пиксель рендера ≈ 10 пикселей
  матрицы), собственный алиасинг матрицы на этом масштабе не возникает; симуляция добавила бы ложный цвет, которого
  реальная камера не показывает.
- **Защита анализа**: ошибка экспозиции и смаз — измерения клиента (ограниченные).
- **Не сделано**: прогон выделенного сервера и двух клиентов (сервер требует EULA, принимает владелец).

## 32. Подводные камни

Всё это уже ломалось (подробнее в `CLAUDE.md`):

- Мод-слои GUI рисуются и при `hideGui` — HUD должен пропускать себя во время захвата.
- Ресайз render target требует прогревочного кадра; прогревочные кадры очищаются в чёрный.
- Рука отменяется всё время использования камеры, а не только при активном видоискателе.
- Углы вида штатива — из поворота игрока за кадр, не из сущности.
- `BakedModelWrapper.applyTransform` теряет проходы — композиты возвращают `this`.
- Меню машин не должны зависеть от клиентского block entity.
- Sodium 0.8 ломается на dev-classpath — `devMods`.
- Компонент record нельзя назвать `wait`.
- Внутри параллельных строковых циклов нет общих временных массивов.
- Элементы моделей в −16..32, поворот ±22.5/45° по одной оси.
- ГРИП собирается слоями (`LensBlur`): гауссова пирамида давала «кашу» без формы диска, а «собирающее» размытие —
  жёсткий контур переднего плана.
- Машины читают карту через `CameraHelper.slotCard` (USB-камеры).
- `Viewfinder.sendSettings` ставит настройки и на клиентский стек.
- Живой ГРИП уменьшает разрешение, чтобы предел радиуса совпадал со снимком; малое размытие — в полном разрешении
  (иначе превью размытее снимка); проба глубины терпит траву.
- Паки `#version … compatibility` на Mesa — только с `allow_glsl_compat_shaders=true`.
