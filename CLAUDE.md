# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

RealCamera: a realistic-photography mod for **Minecraft 1.21.1 / NeoForge** (ModDevGradle, Java 21, Mojang
mappings + Parchment). Public GitHub repo (github.com/HackDanel/realcamera), non-commercial: it uses real camera
brands and model names (nominative use, disclaimer in the README). No monetisation, and no release on
CurseForge/Modrinth without the owner deciding so explicitly; never add manufacturers' images or logos (all assets
must stay generated by tools/gen_assets.py). The owner is not a programmer; Claude writes all code and assets. The full feature plan is in
`~/.claude/plans/mellow-munching-sonnet.md`; what each finished stage delivered (and lessons learned) is in
`docs/stage*.md`. The README (Russian) has the player-facing controls.

## Start of every session

Before any other work, update the local repo from GitHub: `git pull --rebase` on the current branch (the owner may
have pushed from another machine). If the working tree has uncommitted changes or the pull conflicts, stop and tell
the owner instead of stashing, resetting or resolving on your own.

## Commits

Commit after every finished task (on the current branch, under the owner's identity, no Claude attribution). Push only
when the owner explicitly says so.

## Commands

The system Java may be newer than 21; Gradle downloads JDK 21 itself (foojay toolchain).

- `./gradlew build` — jar in `build/libs/`
- `./gradlew test` — JUnit tests (pure-Java optics and image pipeline, catalog consistency, analysis records); they run
  in the NeoForge unit-test environment, the project dir comes in as `realcamera.projectDir`
- single test: `./gradlew test --tests 'dev.hackdanel.realcamera.processing.ImagePipelineTest'` (append `.methodName` for one method)
- `./gradlew runClient` / `runClient2` (second client, nick Player2) / `runServer` (the owner must set `eula=true` in `run/eula.txt` themselves — do not do it for them)
- `./gradlew runClientAutotest -Pautotest=stage1|…|stage7|dof`, and `-Pautotest=stage8 -Pviewer=jei|emi|rei` — unattended end-to-end run in `run-autotest/`: creates a world, builds a scene, shoots, prints, etc. Results are `[autotest] PASS/FAIL` log lines; screenshots go to `run-autotest/screenshots/autotest/`, photos to `run-autotest/screenshots/realcamera/<date>/`. Check results visually by reading those images. The autotest window must not be touched while it runs.
- `-Pviewer=jei|emi|rei` puts that recipe viewer on the dev runtime classpath (any run task); plugins live in
  `client/compat/` and share `RecipeViews`
- `-PcaptureWarmup=N` changes warm-up frames for capture in the autotest run; `-PnoShaders` skips copying Sodium/Iris into run dirs. Iris shaders on/off for the autotest: `run-autotest/config/iris.properties`.

Generators (run from the repo root; their output is overwritten every run, so edit the generator, not the output):
- `python3 tools/gen_assets.py` — all textures, item/block models, blockstates, sounds (`.ogg` via ffmpeg)
- `python3 tools/gen_recipes.py` — everything in `src/main/resources/data/realcamera/recipe/` and block loot tables
- `python3 tools/gen_settings.py` — `component/CameraSettings.java` (record, codecs, `withX` methods; the fields are
  split into codec groups of at most 16, joined with nested `mapPair` — the generator does it, just append fields)
- `python3 tools/gen_catalog.py` — the stage 6 catalog in `tools/catalog.py` (bodies, lenses, mounts, adapters,
  teleconverters, batteries, cards) → registry JSON + en/ru names. `gen_assets.py` and `gen_recipes.py` read the same
  file for models (body `style`, lens `look`) and recipes (tier/kind). Earlier-stage entries are hand-written JSON.
- `python3 tools/gen_loot.py` — structure loot (`realcamera:add_items` global loot modifiers)
- `python3 tools/gen_advancements.py` — the advancement tab + its en/ru names
Run order after editing the catalog: gen_catalog → gen_assets → gen_recipes. `CatalogTest` checks references, flange
rule for adapters, models, names and recipes.

## Architecture

**Data-driven catalog.** Bodies, lenses, mounts, adapters, teleconverters, batteries, cards, flashes,
filters, grips and colour profiles are datapack registries (`registry/RCRegistries`, records in `spec/`),
loaded from `data/realcamera/realcamera/<registry>/*.json` and synced to clients. Items are generic
(`camera_body`, `lens`, …); the concrete model is a `ResourceKey` data component (`registry/RCComponents`).
Adding equipment = an entry in `tools/catalog.py` (or JSON + model + lang keys `realcamera.<registry>.<ns>.<path>` +
recipe by hand). Compact cameras: the body names a `fixed_lens` on the pseudo-mount `realcamera:fixed`; the body
item fills its lens slot itself and the parts menu locks it. Built-in storage (X2D) works the same way: card form
`internal_*`, the body fills and locks its card slot; the computer and printer accept any digital camera with a card
in it (USB, `CameraHelper.usbCard`). What a body can do is in its spec, not in code: allowed exposure modes and meter
type of film bodies (`Film.modes/meter`), shutter types (`CameraBodySpec.shutterTypes`: no e-shutter on DSLR/film,
`efcs`, `full_mech`), leaf shutter (`Shutter.leaf`, any-speed flash sync), e-shutter flash on fast readouts,
`battery_drain` = battery capacity / CIPA shots (fractional, rounded at random per shot).
Mojang record codecs allow at most 16 fields per group: use nested records (see `CameraBodySpec`) or the
settings generator.

**Optics always go through `camera/OpticalChain`** (body → adapter → teleconverter → lens, effective sensor
with APS-C crop/image circle, effective focal/aperture, AF speed, EXIF lens name). Camera parts live in the
`CameraParts` component (8 slots); wear in `CameraWear`.

**Common vs client.** Client-only code is under `client/` (loaded via `@Mod(dist = CLIENT)` and
`@EventBusSubscriber(value = Dist.CLIENT)`). Common code reaches the client only through `ClientBridge`
(implemented by `client/ClientBridgeImpl`); server→client payloads are registered in common code and
dispatched via `ClientBridge.handlePayload`.

**Photo pipeline (end to end).**
1. `client/camera/Viewfinder` — camera at the eye (or on a tripod): FOV from focal length, metering
   (`SceneMeter` converts game light to real EV: shade/night/rain calibrated, reflected-light meter via map-colour
   albedo, scene colour temperature), `optics/Exposure.solve` (P/A/S/M), AF/subject detection, drive modes, the
   camera buffer (drains at the card's write speed), shutter. Composes a `PhotoCapture.Shot`. A correct exposure
   renders the metered area at middle grey however dark the game drew it (`PhotoCapture.relight`). The reference is NOT the metered area
   (that made the whole picture follow the spot/centre aim in M): photo and EVF are developed against the incident light
   and light curve averaged over all surfaces in the frame (`Viewfinder.developEv/developGameLight`, Shot.sceneEv/gameLight;
   the meter needle `Exposure.Result.delta` stays the reflected reading). Then `processing/ShadeMap` puts each region at
   its real light (2^(EV here - ref) / game light ratio: shade 2-3 stops darker than the game's flat curve) — photo:
   192-wide ray grid (`CameraRays.grids()[4]`, edge-aware upsampled); EVF: `Viewfinder.shadeMap` 48-wide over the
   frame x1.25, cast a quarter of its rows per tick in the orientation the pass began with, each cell with its distance;
   texture `LightMap` (R correction, G log distance) in `realcamera_evf`: every pixel is re-projected into the map by
   its depth and the camera's turn/move since (`MapRot*`/`MapShift`), and only cells at about its own distance count
   (a 24-wide bilinear map left soft blotches across block edges and slid with the screen while panning). Off with a shader pack (it draws its own shading). Light sources (torches, lamps, lava: blocks with
   light emission under each pixel, found from the GPU depth by `CameraRays.emitters`) are then raised to their real
   luminance vs the metered EV (`processing/LightSources`, before the DoF so bokeh discs carry it); the light is the
   texels near the block's brightest pixel in the frame (flame yes, torch stick no).
   Electronic finders (`evf`/`hybrid`/`none`, digital bodies) show the photo's look live: `client/render/EvfPreview`
   (shader `realcamera_evf`, after the live DoF) applies the per-pixel part of the development — relight of a dim
   scene (with a pack: `FrameSampler.meteredLuminance` + `ShaderCompat.packRelight`), exposure error, colour filter,
   GND, vignetting + correction, noise, clipping, WB, roll-off, profile. Parameters come from the same
   `PhotoCapture.digitalParams` as the photo; `processing/LiveView` is the Java reference of the shader (tested
   against the pipeline in `LiveViewTest`, also feeds the histogram) — change both together.
   AF rays hit block outlines (grass and flowers count). AF needs local contrast (`hud/FrameSampler.contrastAt`,
   the frame read back before the GUI): too little and the lens hunts and fails; it lands with a random error of
   a fraction of the wide-open depth of focus. AF-ON (R) is back-button focus. `client/render/DofPreview` blurs
   the viewfinder live from the depth buffer (three passes, shaders in `assets/realcamera/shaders/`; off during
   capture and on rangefinders). Depth becomes blur radii at AFTER_LEVEL (the depth buffer is cleared before the
   hand/GUI); the blur itself runs at once without a shader pack, or at `RenderGuiEvent.Pre` with one (Iris draws
   its final picture after AFTER_LEVEL); the AF contrast is sampled at the same point, before the blur.
2. `client/capture/PhotoCapture` — renders one clean frame at sensor resolution by temporarily resizing the
   window/main render target (one warm-up frame first), reads it back together with the depth buffer of the same
   frame (`RenderLevelStageEvent` AFTER_LEVEL, linearised with that frame's projection), and ray-casts depth and
   light grids (`CameraRays`). The per-pixel GPU depth is used when it agrees with the ray grid
   (`DepthUpsampler.agrees`; a shader pack may leave something else in the depth buffer), otherwise the grid is
   upsampled. Exposures ≥ 1/4 s accumulate every frame through PBOs. Without a shader pack the depth is also copied
   before and after the translucent blocks (`client/render/DepthLayers`): `processing/LayeredDepth` focuses through
   water (apparent depth, /1.33), stained glass and ice. Stained/tinted glass has an empty visual shape, so the
   rays pass it: a second COLLIDER ray marks those cells `GLASS` (`CameraRays.glassBefore`); its texture frame (outer
   1/16 of a face, `LayeredDepth.onGlassFrame` from the surface depth) keeps the glass depth, the middle gets what lies behind. Without a pack `agrees` compares `LayeredDepth.rayView` (opaque
   world + water surfaces: the rays stop at water, pass through stained glass, miss particles and rain) and
   `dropFixedLayer` is skipped (particles are flat billboards facing the lens; smoke was dropped as a "fixed layer").
   Rain/snow write depth on Fast/Fancy while depth is wanted (`mixin/client/LevelRendererWeatherMixin`); Fabulous: the
   weather target. Development runs on a worker thread.
   With a shader pack the window is NOT resized (`Active.noResize`): a resize recreates the pack's buffers and resets
   its auto exposure, temporal accumulation and title timer (IterationT showed a grey frame with "Iteration 3.2.0");
   the frame is rendered at window size (taller FOV if the window is narrower than the sensor) and the centred crop
   with the sensor aspect is the photo (`fw/fh/cx/cy`).
3. `processing/ImagePipeline` + `ImageParams` — pure Java (no Minecraft classes, unit-tested): exposure,
   DoF/bokeh, flash, motion blur, rolling shutter, distortion/CA, vignetting, wear, flare, noise, colour.
   `optics/` is pure Java too. Keep both packages free of game classes. Special optics: fisheyes render a capped
   wide rectilinear frame (`Optics.renderVfovDeg`) and `ImagePipeline.fisheye` remaps it; a shifted tilt-shift lens
   renders the frame pitched up by atan(shift/f) (`ComputeCameraAngles`) and `lensShift` re-projects it; tilt
   changes the focus distance per row (`Optics.tiltedFocusM`); bokeh styles smooth/busy/swirl/bubble. Depth of field:
   `LensBlur` + `BokehKernel` (one disc shape for every pixel and for the bokeh highlights).
   The layer loops of `LensBlur` (downsample, disc convolution with `BokehKernel`'s exact taps per tile variant,
   "over" composite, the behind-copy) can run on the GPU: `processing/GpuBlur` (pure interface + `kernels()` tables),
   `client/render/GpuLensBlur` (raw GL 3.2, one layer per render-thread step, all GL state saved/restored). It picks
   itself: first job GPU, next CPU, then the faster (GPU only if 1.5x faster; a step over 250 ms disables it).
   Java stays the reference and the fallback; `-PcpuDevelop=true` (`realcamera.cpuDevelop`) forces Java.
   Motion (`processing/MotionBlur`): the frame is mid-exposure; the world smears by shake + pan, plus parallax if the
   camera moves; moving entities (`CameraRays.motionField`, captured with the ray grid) are layers smeared over a
   filled-in background, so panning with a runner keeps it sharp; flash light is a separate sharp layer (front/rear
   curtain). Axial colour runs the DoF twice (green vs red/blue radius). Long exposures add dark current from the
   sensor temperature (`client/camera/SensorHeat`) and hot pixels unless long-exposure NR is on.
4. Export: full-size JPEG with EXIF (`processing/ExifWriter`) and optional RAW to `screenshots/realcamera/`.
   RAW = output of `ImagePipeline.developSensor` (before lens corrections `correctLens` and `finish`: white balance,
   roll-off, profile) as a 16-bit linear PNG +
   JSON sidecar (`processing/RawFile`); `client/photo/LocalOriginals` remembers which local files belong to which
   photo id. A downscaled JPEG goes through `client/photo/PhotoUploader` (sequential queue; camera shots and editor
   saves share it).
5. Server: `network/ServerPhotoService` validates (quota, rate, JPEG header), stores files under
   `<world>/realcamera/photos/`, indexes them in SavedData (`photo/PhotoIndex`, `photo/CardStorage` — card
   contents live on the server, the card item only mirrors usage), streams downloads with a bandwidth budget.
6. Film: a film body (`CameraBodySpec.film`) takes a `FilmRoll` in the card slot; frames are uploaded as latent
   index entries keyed by the roll id (like a card) and only become visible after `photo/FilmLab.developRoll`
   (developing tank). Darkroom light checks: `gameplay/Darkroom`.
7. The computer's editor (`processing/PhotoEditor`, pure Java; `client/editor/EditSession` loads the local
   original or the in-game copy and renders previews on a worker) saves results as new photos
   (`PhotoMeta.editedFrom`). Files are removed only when no card references them and they were never printed.
8. Clients show photos via `client/photo/PhotoCache` (LRU GL textures + per-server disk cache): prints
   (`PrintItemRenderer` BEWLR), wall frames (`PhotoFrameRenderer`), playback/printer screens.

9. Game goals: the `Shutter` packet carries a `ShotInfo` (nonce); `analysis/FrameAnalyzer` analyses the frame on the
   server from its own world state and the result waits by nonce for the upload (`PhotoMeta.analysis`).
   `gameplay/PhotoEvents.photoStored` (digital: on store; film: on development) feeds the encyclopedia
   (`gameplay/Journal`, player attachment, synced with `JournalSync`) and the advancement triggers
   (`gameplay/RCTriggers`); other deeds go through `PhotoEvents.count/event`. Newspaper orders: `component/Commission`
   on a trade cost, matched by `mixin/ItemCostMixin`; `MerchantContainerMixin`/`MerchantResultSlotMixin` tell it the
   seller (`Commission.TRADER`) and record sold pictures (`gameplay/SoldPhotos`, by original shot). The analysis
   biome is the focus point's (`PhotoMeta.sceneBiome`); frames developed while their author is offline are credited
   at login (`gameplay/PendingCredits`); lightning during an open shutter is added via `lightningStruck`.

10. Flash in multiplayer: the `Shutter` packet carries the guide number the flash really gave (TTL power); the server
   clamps it to the flash spec and sends `FlashPop` (position above the lens, lens axis, GN) to players within 160
   blocks (the photographer included). `client/render/FlashGlow` shows it to observers from the light it
   adds relative to the ambient EV over the eye's ~0.1 s (beam cone `PhotoCapture.flashCone`, occlusion by ray casts):
   multiplicative scene brightening, source glare and an afterimage, drawn at `RenderGuiEvent.Pre` so shader packs do
   not matter. `PhotoCapture.remoteFlash` adds other photographers' flashes to an open exposure as a per-pixel light
   grid with shadows (`ImageParams.Extras.otherFlash`).
11. Shader packs: `mixin/client/IrisCenterDepthMixin` (@Pseudo, Iris optional) overwrites Iris's `centerDepthSmooth`
   with the lens focus distance while the camera is raised, so a pack's own DoF focuses with the lens.
   `client/render/ShaderCompat` (Iris API by reflection) — pack in use, shadow pass (level-stage
   handlers skip it), depth-buffer trust (probed against rays every 40 frames, plus the photo's own
   `DepthUpsampler.agrees`; the live DoF is off while untrusted), and `packRelight`: with a pack the photo is
   brightened from what the pack drew in the metered area vs the surfaces' reflectance (`PhotoCapture.Metering`),
   bounded to ±3 EV around the vanilla light curve. With a pack the capture does not resize the window (see 2).

**Holding the camera.** `CameraBodyItem` has no vanilla use animation (SPYGLASS would win over the item's arm
pose). `client/render/CameraItemExtensions`: third person returns the two-handed `CameraPose.ARM_POSE` (an
`HumanoidModel.ArmPose` added by `META-INF/enumextensions.json`), and `SpecItemModels.Composite.applyTransform`
counter-rotates the camera while a raised camera is drawn (`CameraPose.raisedNow`, set in RenderPlayerEvent); first
person animates the raise/lower over `Viewfinder.RAISE_TICKS`, and the viewfinder only activates after it. A camera in
the inventory but not in a hand hangs on the chest (`gameplay/NeckCameras` sends `NeckCamera` to trackers,
`client/render/NeckCameraLayer`): lens forward, back against the chest (and armour), drawn with `ItemDisplayContext.NONE`
and placed by the bounds of all render passes so any lens stays outside the body; it tilts about the back edge that
touches the chest (lens-down while standing, swings out when sneaking). Own flash: the server sends `FlashPop` to the photographer too; `FlashGlow` defers
pops while a frame is captured and gives the own flash (shooter = local player, hand or tripod) only the scene
brightening, no source glare/afterimage (issue #9). Glare/afterimage scale continuously with the stops above the eye's
adaptation.

**Filters** are generated from `FILTER_KINDS` in `tools/catalog.py` (kind × thread sizes, key `<base>_<size>`):
gen_catalog writes the JSON + names, gen_assets the icons, gen_recipes the recipes. Kinds: nd, cpl, uv, color
(per-channel, also 80A/85), mist (`ImagePipeline.mist`), gnd (`graduatedNd`), star (`star`, point-like sources only).
`FilterSpec.fits(thread, ring)`: diameter == lens thread, or through a step-up ring (`STEP_UP_RINGS` in the catalog,
registry `step_up_ring`, issue #7): ring input == thread, filter ≥ ring output; none on thread 0 (fisheyes, compacts).
The ring rides on the filter (`STEP_UP_RING` component on the filter stack), so the optics read the filter as before;
they are screwed together/apart by clicks in any slot (`AccessoryItem` overrides), a bare ring may sit in the
camera's filter slot. `CatalogTest.everyThreadTakesAFilter` wants a filter or ring for every lens thread.

Network messages identify a camera with `camera/CameraRef` (a hand or a tripod entity id); the server
resolves it with `ServerPhotoService.resolve`, mutates the stack and must call the handle's `commit()`
(tripod cameras are copies stored in entity data).

**Item models.** `client/render/SpecItemModels` picks the model named in the spec JSON and draws a camera
as several render passes (body + `_mounted` adapter/teleconverter/lens models, shifted along the optical
axis; 1 model unit ≈ 9 mm, shared mount point in `tools/gen_assets.py`).

## Gotchas (all hit before)

- Mod GUI layers still render when `options.hideGui` is set: the viewfinder HUD must skip itself while
  `PhotoCapture.capturing()`, or it ends up in the photo.
- Resizing the render target needs a warm-up frame; the block selection outline is cancelled in the
  viewfinder and during capture. The resized target is blitted to the window at its own size after
  `RenderFrameEvent.Post` (a magnified corner, looks like the view jumping): capture frames are cleared to black.
- The camera's use pose (SPYGLASS) has no first-person transform: the hand is cancelled while a camera is being
  used, not only while the viewfinder is active, or the model is drawn at the eye for a frame.
- Tripod view angles come from the player's per-frame rotation (`TripodView.onCameraAngles`), not the tripod
  entity's (tick rate); camera keys are active on a tripod too (`RCKeys.CAMERA_IN_HAND`).
- `BakedModelWrapper.applyTransform` returns the wrapped model and drops extra render passes — composites
  override it to return `this`.
- Machine menus must not depend on the client block entity (the open-screen packet can arrive first).
- Sodium 0.8 is jar-in-jar and breaks on the dev classpath: Sodium/Iris come from the `devMods`
  configuration copied into each run dir's `mods/`.
- A record component cannot be named `wait` (clashes with `Object.wait()`).
- The pipeline's row loops run as parallel streams: no shared scratch arrays inside them (allocate per row).
- Model elements must stay inside -16..32 and rotate only by ±22.5/45° on one axis: `cylinder()` in gen_assets builds a
  16-sided prism from 8 rotated spokes; very long lenses are shortened to 24.5 units.
- Ray casts see neither grass/flowers/leaves without collision nor the real shape of mobs (only their boxes), so the
  depth map comes from the GPU depth buffer when it can; only the fallback (ray grid) has the old artefacts: grass
  blurred like the ground behind it, a sharp halo around wide-open portraits. Tiny light sources get the blur radius
  of their surroundings.
- Depth of field is `processing/LensBlur` (layers by signed blur radius, each convolved with the aperture disc of
  `BokehKernel`, composited back to front, the foreground layers over each other too, a pixel occluding only in the
  farther of its two layers; holes under the blurred foreground filled from the foreground layers behind, then
  pull-push; summing the foreground layers left smoke at the lens with a hard dark-rimmed edge). A gaussian pyramid
  looked like mush, and a gather blur alone leaves blurred foreground with a hard outline. The live preview
  (`realcamera_dof_*`, `include/dof_bokeh.glsl`) uses the same disc shape; small blur is gathered at full resolution in
  the composite, or the 1/8 pass made the viewfinder blurrier than the photo.
- Outside review fixes (camera mechanics, exposure, optics, film, gameplay) are listed in `docs/review-fixes.md`.
- Machine menus/screens must read the card through `CameraHelper.slotCard` (a camera over USB has no CARD
  component itself; reading the slot item directly showed an empty list for X2D and every USB camera).
- `Viewfinder.sendSettings` also sets the settings on the client stack: raising the camera again before the
  server's slot update arrived read the old focus distance/AF point back.
- The live DoF preview downsamples to 1/2..1/8 so its radius cap (15% of the height) matches the photo; the depth
  probe for packs (`DepthUpsampler.agrees(..., true)`) tolerates grass in front, or the blur toggled with the aim.
- IterationT (and other `#version … compatibility` packs) do not load on this Mesa machine; run the autotest with
  `allow_glsl_compat_shaders=true ./gradlew runClientAutotest …` to test them.
- `-Pautotest=pose`: strap (`strap_*.png`: kit zoom and Z9 + TC-2.0x + 600 mm seen through an invisible armour stand from
  front/side/three-quarter/back, sneaking, in a chestplate), two-handed pose, first-person raise, photos through
  GND/Black Mist/star.
- `-Pautotest=dof`: grass meadow at f/1.8 for checking depth of field; `realcamera.debugDumps` writes
  `raw_<ms>.jpg`/`depth_<ms>.jpg` per shot to `screenshots/realcamera_debug/`.
